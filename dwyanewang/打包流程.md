# Paseo 本地产物打包流程

> 目标：在 Ubuntu 按需构建服务端、Android ARM64 APK 和 Windows x64 zip，并为所选可下载产物启动临时下载服务。
> 版本以根 `package.json` 为准。打包只使用下述版本化入口，不再由代理复制各阶段命令。

叠加冲突续跑与解决复用的设计、边界和初始验收依据见 [rw-main 叠加冲突续跑与解决复用方案](rw-main-conflict-resume-plan.md) 第 13 节。2026-09-16/17 已有两次真实三端打包成功，确认审查缓存和发布失败后的 readiness 复用生效；成功路径中的冲突最终由源修复/lifecycle 处理，尚不能据此声称多个 overlay 连续暂停及自动候选能力测试已完成真实验收。不同请求的源适配工作量不同，不能直接用总耗时推导提速比例。

## 0. 固定环境与 worktree

- 产品构建目录：`/home/yangfei/Projects/paseo`，正常停留在 `rw-main`，长期保留 Android/Gradle/Metro/NDK/Electron 缓存。
- 控制面：独立的 `chore/build-paseo` worktree，只保存 `dwyanewang/` 下的清单、脚本和文档，不合并进产品分支。
- `main` 只包含真实上游历史；每轮首次同步到 `upstream/main`，本轮后续重试固定该快照，不追赶中途的新提交。`rw-base` 以追加历史保存长期本地功能；`rw-main` 由 `rw-base` 和 [`rw-main-branches.txt`](rw-main-branches.txt) 中的临时叠加分支按顺序重建。
- 不直接在 `rw-base` 或 `rw-main` 修改产品代码。长期功能只通过 `manage-rw-base.sh promote|maintain` 进入基线；临时上游候选才进入叠加清单。
- 不拉取代码的测试构建可以在同一把构建锁内创建 `rw-local-build-*` 临时候选并叠加显式本地分支。该候选不写清单、不移动 `rw-main`、不推送，构建成功或失败后都恢复产品 worktree。
- worktree 共享 Git refs，但源码、`node_modules`、`dist` 和构建缓存独立。任何相关 worktree 有改动或 detached HEAD 时停止，不 stash、不覆盖。
- 工具版本来自 `.tool-versions` / `.mise.toml`；脚本会在自己的 shell 中安装并激活 mise。Wine 只使用 `~/.local/share/paseo/wineprefix`，绝不删除默认 `~/.wine`。
- 禁止重启或触碰 6767 主 daemon。

先定位控制面：

```bash
paseo_build_root=/home/yangfei/Projects/paseo
paseo_chore_root=$(git worktree list --porcelain | awk '
  /^worktree / { path = substr($0, 10) }
  $0 == "branch refs/heads/chore/build-paseo" { print path }
')
[[ -n "$paseo_chore_root" ]]
```

## 1. 完整同步与 readiness gate

除非用户明确要求“不拉取/不同步”，本轮首次从控制面调用。将用户消息时间记录为 epoch 秒 `paseo_requested_at`；无法恢复消息时间时须标注改用首次命令时间，不能声称覆盖此前等待：

```bash
paseo_preflight_state="$paseo_build_root/.dev/build-paseo-preflight.env"
paseo_run_id="$(date +%Y%m%d-%H%M%S)-$$"
bash "$paseo_chore_root/dwyanewang/prepare-rw-main-for-build.sh" \
  --build-root "$paseo_build_root" \
  --run-id "$paseo_run_id" --requested-at "$paseo_requested_at" \
  --state-file "$paseo_preflight_state" \
  --push
```

用户明确要求新增项时，在同一命令末尾按用户给出的顺序追加：

```bash
--add-pr 2345
--add-branch feat/example
--update-pr feat/existing 3456
```

新 PR 不自动发现。`--add-pr` 只接受 `dwyanewang` 拥有的上游 PR 并自动解析源分支；`--add-branch` 只用于需要持久进入正式 `rw-main`、并随 main 前进做语义审查的个人叠加分支。长期个人功能使用第 1.3 节的 `promote`。一次性不拉取测试使用第 2 节的 `--local-branch`，不要写入持久清单。

`--update-pr BRANCH NUMBER` 只更新已列分支，验证新 PR 为 OPEN、owner 与 head branch 匹配、源分支已同步 origin；它不绕过 main/head 的语义审查，不按标题猜 PR。显式重映射先于旧 PR 的 MERGED 自动移除判定：旧 PR 即使已被 main 包含，也不会使新映射被自动删除，是否仍需保留由常规语义审查判断。一次收齐全部变更，request 轮和 accept 轮原样重传新增/重映射参数；审查收敛后统一提交清单。退出码 3 尚未写清单，不能在接受轮遗漏新增项。

每轮还会校验所有已有条目的 PR owner 为 `dwyanewang`、head branch 与清单分支完全一致；不匹配即停止并要求显式重映射。已有条目允许 CLOSED（未合并），OPEN 要求只适用于新增/替换 PR。引入或调整这项门禁时，先批量只读查询清单 PR 的身份，不能把离线测试通过当作真实清单已经匹配。

prepare 的 `--run-id` 是必填参数；漏传时在同步、创建请求目录或删除 ready state 前退出，不自动生成新请求。仅真正的新打包请求才生成新 ID，显式换 ID 仍意味着新请求，不是恢复旧请求。首次同步后保存本轮 `main.snapshot`，并把 `<sha> <epoch> initial` 追加到独立的 `main.refreshes`；显式刷新追加 `refresh` 事件，不能改成覆写 snapshot 内的多行历史。后续所有 prepare（接受审查、源分支修复重试、提交清单后重建）都使用同一 `--run-id` 并加 `--no-fetch`；不重复传 `--requested-at` 也会沿用初始时间。漏传 `--no-fetch` 会拒绝，不自动推进 main。确实要纳入更新上游时改用 `--refresh-main`，它重新同步并保存快照，旧审查由精确坐标门禁拒绝；刷新与接受必须分开。`--no-fetch` 仍执行所有审查/readiness 门禁，与跳过同步的产物模式 `--skip-preflight` 不同。

冻结期内共享 tracking refs 可以前进，但本地 main 必须等于快照且仍是 upstream/origin main 的祖先；`rw-base`、base candidate、每条 overlay 均不得引入已知的快照后上游历史。源分支修复 rebase 本轮快照 main，而非当前 tracking tip。PR 在快照之后才被上游合入时本轮保留，直到快照包含其 merge commit 才能自动移除。显式冻结把新上游冲突的发现留到下一次刷新/构建；交付时必须报告快照 SHA 和时间。

前置脚本统一完成：

1. 检查控制面、构建目录、`main` 及清单功能分支 worktree 的洁净度。
2. 首次或显式刷新时 fetch upstream/origin，将本地 `main` 安全快进并推送 fork；`--no-fetch` 只验证已冻结坐标。
3. 批量查询清单 PR，自动删除已经合入且被本地 `main` 包含的项。
4. 按每项的 `reviewed-main` / `reviewed-head` 判断是否需要语义审查。
5. 在输出语义审查 request 前，在临时 detached worktree 中只读模拟 `rw-base + main + overlays` 的实际合并顺序。支持的文本/`.patch` 冲突只诊断具体阶段和路径，继续原 exit 3/4 审查与清单流程；二进制、子模块或未支持的结构冲突仍阻断。预检不解决冲突、不学习 rerere、不移动正式 refs、不改清单、不安装依赖、不运行构建。
6. 将本轮 main 快照合入候选 `rw-base`，再按清单顺序叠加全部临时分支生成完整候选 `rw-main`；不是每层各跑一遍。stamp miss 时先构建 server 共用依赖和 app audio 依赖，立即运行一次真实 app typecheck，再构建 server/CLI，最后仍运行完整 format/typecheck/lint。这样 app 组合错误不会等 server/CLI 构建结束才暴露。没有待审、接受或移除动作的最终轮不重复做临时 mergeability；实际候选合并仍会检查冲突。
7. 检查通过后才移动本地 refs，并用一个 atomic push 同时更新 `origin/rw-base` 与 `origin/rw-main`。
8. 成功时原子写 ready state 和 workspace 构建可信 stamp；失败或暂停前删除旧 ready state，防止复用过期结果。

前置脚本在删除旧 state 前取得 `$paseo_build_root/.dev/build-paseo-artifacts.lock`，并持有到整个同步、审查 gate 和重建流程结束。正式产物脚本与 `manage-rw-base.sh` 使用同一把非阻塞锁。ready state 冻结控制面 HEAD、`main`、`rw-base` 与 `rw-main`；正式脚本取得锁后会再次验证全部坐标，任一漂移都停止且不删除旧产物。

readiness stamp 允许同一请求中的安全去重：不同 merge commit 若 Git tree 完全相同，并且 `.tool-versions` / `.mise.toml`、实际 Node/npm 版本、所有依赖与 patch 输入、server/CLI/protocol 等完整 `dist` 摘要都匹配，可复用先前已经通过的 readiness。tree、工具链、依赖输入或任一产物变化都会 cache miss，并依次执行 `build:server-deps`、audio workspace build、app typecheck、server build、CLI build、`format:check`、全仓 `typecheck` 和 `lint`。固定工具链的安装与激活由 `rebuild-rw-main.sh` 统一拥有，prepare 和 lifecycle 每次 rebuild 都只激活一次。正式产物链只接受 exact HEAD 的 stamp；缺失、畸形或损坏时安全回退完整 server build。

### 1.1 退出码与语义审查

- `0`：普通 prepare 表示 readiness gate 已通过，可以使用生成的 ready state 进入第 2 节。`No-op:` 表示 main、清单和全部分支 head 未变化，可安全复用现有 merge 链。带 `--record-review-result` 时仅表示证据记录成功（`PASEO_PREFLIGHT_STATUS=review-recorded`），不会重建或生成 ready state，不能据此启动产物链。
- `3`：不是脚本故障。脚本会打印 `PASEO_REVIEW_REQUEST_FILE=<绝对路径>`，其内容寻址 TSV 冻结本轮 main 与每条分支的精确审查区间。必须审查 request 中的每一项；阅读全部提交主题、路径，疑似相同能力时继续看 PR 说明和完整 diff。patch 等价或路径重叠只是线索，不是语义结论。
- mergeability 预检发现支持的文本冲突：属于诊断，不阻断语义审查。完成 exit 3/4 后，rebuild 在隔离 operation 中从 sync 第 0 步开始组装，冲突时退出 `6` 并保留现场。未支持冲突或普通 Git 错误仍立即失败。
- `4`：清单已原子更新，但尚未重建。按第 1.5 节校验，统一提交 `chore(build): sync rw-main branches` 并推送 `origin/chore/build-paseo`，保留 `--run-id --no-fetch`、不带增删/重映射/接受参数重跑。
- 其他非零：立即停止并按日志诊断。没有 ready state 时禁止启动服务端、Android 或 Windows。

语义审查的自动决策：

1. 上游未吸收：保留该分支。
2. 上游已完整吸收：重跑时传 `--remove-branch <分支>`。
3. 上游只吸收一部分：到源功能分支自己的 worktree rebase 本轮 main 快照、删除重复实现、运行定向验证并 `git push --force-with-lease`，再重新审查。
4. 无法立即确定：AI 继续检查完整 diff、`git range-diff`、路径、测试和上游上下文；仍无法证明完整吸收时默认 `keep`，不得自动删除。整个接受/删除决策由 AI 完成，不等待人工确认。

只有一个简单分支时由主代理直接审查。有至少两个独立待审分支时，主代理按 request 的冻结区间启动最多 3 个只读 reviewer subagent 并行审查；reviewer 不得改 worktree、移动 refs 或运行测试，每条分支单独返回结论和证据。主代理必须核对 request 的分支集合与返回集合完全一致，并且仍是唯一的接受、清单修改、提交和推送决策点。

若某一分支已经得到完整 `keep|remove` 结论、但同一 request 中另一分支必须回源修复，须在其他分支 head 改变之前把证据写入文件，并用同一 run 记录该分支结果；旧 request 的任一 head 已改变时，先生成新 request 再记录：

```bash
bash "$paseo_chore_root/dwyanewang/prepare-rw-main-for-build.sh" \
  --build-root "$paseo_build_root" --run-id "$paseo_run_id" --no-fetch \
  --record-review-result "$paseo_review_request_file" BRANCH keep EVIDENCE_FILE
```

后续 request 只重列键变化或尚未记录的分支。缓存键只包含冻结 branch 行、PR 映射和审查规则哈希；它不能免除依赖替代核对、冲突双父审查、候选能力检查或 readiness。`remove` 结论仍须在最终接受命令显式传相应 `--remove-branch`。

记录命令必须使用已有快照的同一 `--run-id --no-fetch`。成功后立即结束，不继续 rebuild，也不更新清单的接受坐标；证据为空或 request 失效仍返回失败。待全部审查完成后另行接受清单，再提交和重建。

等所有 reviewer 返回最终结论，核对集合与精确区间一致、全部项目只能保留或删除后，用同一个前置命令保留新增/重映射参数并追加（中间 keep 不算最终结论）：

```bash
--no-fetch --accept-review-request "$paseo_review_request_file"
```

其中 `paseo_review_request_file` 取自本轮 `PASEO_REVIEW_REQUEST_FILE`；不要只传 main SHA。若审查期间 main、任一分支 head、待审集合或区间变化，脚本会拒绝旧 request，必须重新审查。若同时删除条目，再追加对应 `--remove-branch`。清单坐标变化同样属于清单改动，按退出码 `4` 的要求提交。提交正文记录审查区间和删改依据。

### 1.2 readiness 失败处理

- 支持的文本冲突按第 1.5 节在 operation 内解决，不因冲突存在就默认回源。需要修改非冲突文件、做部分吸收后的删重、处理未支持冲突，或明确安排源维护时，才转为源修复/适配。审查发现类型或接口删除/替换时，应检查调用方是否仍引用旧符号；没有文本冲突不代表组合兼容。
- 网络、SSH、远端查询或推送失败不等于候选验证失败。先检查原始错误和 operation 状态；网络恢复后，普通 prepare 使用原 `--run-id --no-fetch`，lifecycle 使用原父 request 的 `continue --operation`。输入未变时仍可复用 readiness。进入 `publishing`/`awaiting-ready` 后不得 abort，也不要仅凭退出码修改源 refs 或重开请求。
- 同一 workspace 的 `src`/测试 import 报成员不存在、helper 改名或参数不符，通常是分支组合不兼容。临时叠加层回源功能分支修复；长期功能从维护分支经 `manage-rw-base.sh maintain` 进入。不要直接修改候选、`rw-base` 或 `rw-main`。
- 回源分支做 typecheck/定向测试前先确认该 worktree 的依赖已引导（至少 `node_modules/.bin/tsc`、相关 workspace 依赖可解析）；若只是缺依赖，在源 worktree 执行 `npm install --ignore-scripts` 后重跑，不要把环境缺失当成代码冲突，也不要在审查阶段给所有 worktree 无条件联网安装。
- 只有报错实际跨 workspace 指向生成的 `dist/*.d.ts` 时才先重建声明拥有方：protocol/client 用 `npm run build:client`，server/CLI/relay 链用 `npm run build:server`。
- app typecheck 若只把真实存在的 `src/app` 页面报成非法路由，先检查 `.expo/types/router.d.ts` 是否仍来自旧 checkout；正式 readiness 和 `--local-branch` 路径会在 typecheck 前按完整候选路由树重新生成它，不能手工修改候选或把合法 route 强转为宽类型。
- 源分支修复后运行相关单个测试、format 和 lint；typecheck 按第 1.5 节由提交 hook 或显式命令承担，不重复执行。app Playwright 定向测试必须显式清空外部密码：`PASEO_PASSWORD= npm run test:e2e --workspace=@getpaseo/app -- <spec>`。这类可选验证同一时刻只能有一个 invocation，不得与 prepare、lifecycle、readiness、`build:server` 或 pre-commit hook 并行。Metro warmup 超时先记录 document/bundle 阶段、URL、耗时、进程状态与近期输出；只有改变了一个明确条件才允许最多重试一次，仍失败就保留证据并放弃这项可选验证，不能连续重启四轮拖住正式 gate。
- 完整排查按错误文本查询 [踩坑记录.md](踩坑记录.md)，不要每轮预读全文。
- 源分支定向测试若断言 Git 报错文案，用 `LC_ALL=C LANG=C LANGUAGE=C npm exec -- vitest run <文件> --bail=1`（从所属 workspace 执行，app 加 `--project unit`）。不要因本机中文输出而修改产品逻辑；候选能力测试已在函数作用域内固定同样的 locale。

### 1.3 `rw-base` 功能生命周期

状态直接来自 `rw-base` 第一父链上的结构化 trailers，不另建容易漂移的功能清单：

```bash
bash "$paseo_chore_root/dwyanewang/manage-rw-base.sh" \
  --build-root "$paseo_build_root" status
```

`status` 按第一父链提交中的 `Paseo-Base-Feature` / `Paseo-Base-Action` trailers 重建生命周期状态，并把无法归类为 lifecycle 或合法 main sync merge 的提交显式输出为 `UNMANAGED\t<SHA>\t<subject>`。`promote/maintain/retire` 遇到这些提交会拒绝自动推断。用户若说明某项修改已经直接提交并 push，必须先核对真实提交和祖先关系：

```bash
git log --first-parent --decorate --oneline -n 30 rw-base
git show --stat <commit>
git merge-base --is-ancestor <commit> rw-base
```

不能因受管功能列表未显示就推断“尚未迁入”并再次 promote。发现 `UNMANAGED` 时暂停自动生命周期操作，检查当前树是否仍保留其语义并制定显式迁移/清理方案；祖先关系只证明提交进入过历史，不证明后续冲突解决没有丢掉内容。

若完整语义审查已经证明某个历史直提提交被现有 active 功能接管，不删除或改写已推送提交。应在修复该功能的同一次维护操作中追加 `--adopt-commit`：

```bash
bash "$paseo_chore_root/dwyanewang/manage-rw-base.sh" \
  --build-root "$paseo_build_root" --run-id "$paseo_run_id" \
  --state-file "$paseo_preflight_state" --push maintain \
  --feature unistyles-ndk-version --branch fix/unistyles-registration-dedup \
  --adopt-commit a43b1abeb42dcd2a8b143ede55a55bba69520026
```

`maintain` 只接受当前 status 中真实存在的 `UNMANAGED` 第一父提交，并在 lifecycle merge 中写入可审计的 `Paseo-Base-Adopted-Commit` trailer。后续 `status` 会把它计入对应功能的 `adoptions`，不再阻断生命周期；其它未显式接管的提交仍会阻断。该机制只记录已经人工证明的迁移关系，不按标题、作者日期或相似 patch 自动猜测。

迁入新功能；首次迁移可重复提供 feature/branch 对：

```bash
bash "$paseo_chore_root/dwyanewang/manage-rw-base.sh" \
  --build-root "$paseo_build_root" --run-id "$paseo_run_id" \
  --state-file "$paseo_preflight_state" --push promote \
  --feature worktree-checkout-branch --branch feat/worktree-checkout-branch \
  --feature codeup-forge --branch feat/codeup-forge
```

来源分支必须洁净且与 `origin/<branch>` 精确一致。追加修复使用 `maintain --feature ID --branch BRANCH`。每个 promote/maintain 都生成独立 `--no-ff` merge，并记录 feature/action、source branch/head 和 main head trailers；禁止绕开入口直接提交产品变化。

上游提供替代方案后显式退役：

```bash
bash "$paseo_chore_root/dwyanewang/manage-rw-base.sh" \
  --build-root "$paseo_build_root" --run-id "$paseo_run_id" \
  --state-file "$paseo_preflight_state" --push retire \
  --feature codeup-forge --replacement 'getpaseo/paseo#1234'
```

退役不会盲目 revert。脚本从最新 `main` 开始，按原顺序重放其它 active 功能，验证候选后生成 append-only retirement commit，再原子发布 `rw-base`/`rw-main`。若 main 合并、功能 merge 或重放发生冲突，退出码 `5` 会打印 `PASEO_RW_BASE_OPERATION=<request>` 并保留隔离 worktree；解决并 `git add` 后运行：

```bash
bash "$paseo_chore_root/dwyanewang/manage-rw-base.sh" \
  --build-root "$paseo_build_root" --push continue \
  --operation "$paseo_rw_base_operation"
```

尚未进入发布阶段时，放弃可将 `continue` 换成 `abort`。request 内容寻址并冻结 control/main/base/source 坐标；不属于本操作发布过程的 ref 漂移会拒绝继续。冲突或验证失败不会发布候选，旧 ready state 会失效；若发布已经开始，保留父子 operation 并继续收尾，不能 abort。

构建请求中的 lifecycle 新操作必须同时传原 `--run-id` 和正式产物使用的 `--state-file`。run-bound 模式在取得共享锁后读取该请求的 `requested-at` 与 `main.snapshot`，不 fetch、不移动本地 main、不 push `origin/main`；tracking refs 后续可以前进，但冻结 main 必须仍是 upstream/origin tip 的祖先。operation request 继续精确冻结 control、main、rw-base input 与 source heads；`continue` 复用其中的 run 身份且不隐式 fetch，仍拒绝本地 main、control、非本操作预期的 rw-base 值、source head 或请求 snapshot 漂移。lifecycle 把 `--frozen-main` 传给 rebuild，并在 ready state 中保留 run ID、请求起点和冻结时间，因此产物链可直接关联原请求并计算完整墙钟，不再额外调用 prepare。state 写入失败返回非零并打印保留的父子 operation；refs 已成功时修复状态目标后，对父 request 再运行 `continue --operation` 补写，不能另起 prepare 留下父现场。

不带 `--run-id` 的 standalone lifecycle 保持原语义：新操作先 fetch upstream/origin、把本地 main 快进到最新 upstream 并同步 origin；冲突 `continue` 先刷新 tracking refs，并要求所有冻结 remote 坐标仍精确相等。不要把 standalone 路径插入一个已开始的打包请求，否则它仍会主动换 main 代次。

### 1.4 `rw-base` 冲突续跑的双父语义校验

`continue` 前不能只消除冲突标记或复用某个旧候选树。先固定冲突合并的两个父提交，并查看 index 中双方原文：

```bash
paseo_conflict_worktree="$(dirname "$paseo_rw_base_operation")/worktree"
paseo_conflict_ours="$(git -C "$paseo_conflict_worktree" rev-parse HEAD)"
paseo_conflict_theirs="$(git -C "$paseo_conflict_worktree" rev-parse MERGE_HEAD)"
git -C "$paseo_conflict_worktree" ls-files -u
git -C "$paseo_conflict_worktree" show :2:<冲突路径>
git -C "$paseo_conflict_worktree" show :3:<冲突路径>
```

解决并 `git add` 后，必须分别对照两个父提交审查 staged 结果：

```bash
git -C "$paseo_conflict_worktree" diff --cached "$paseo_conflict_ours" -- <冲突路径>
git -C "$paseo_conflict_worktree" diff --cached "$paseo_conflict_theirs" -- <冲突路径>
```

强制规则：

- `add/add` 只表示双方新增了同一路径，不表示任选一侧。双方提供不相交能力时，结果必须取语义并集。
- 冲突文件是 `.patch` 时，逐个检查其中的 `diff --git` 目标；不同目标全部保留，同一目标按 hunk 合并，不能把整个 patch 文件当作普通文本二选一。
- package、patch 路径或 prefix 的 postinstall 注册最终只能保留一份；合并后显式计数，不能因双方都注册而重复执行。
- 以前失败或未经双父验证的候选树只能作为证据，不能作为“已验证模板”复制；树相等不等于语义正确。
- 候选树会静态检查 `scripts/postinstall-patches.mjs`：同一 `(cwd, nodeModulesPath, patchPrefix)` 只能注册一次，同一 patch 文件在一个 cwd 只能应用一次，patch 内部目标必须属于注册的 package；无法可靠解析或映射时直接失败。
- 现有流程本来需要运行 `npm install` 时，脚本会比较旧、新 patch 及注册表，精确删除新候选注册表中的全部 patch-managed package 根目录，再用这同一次安装从缓存恢复。原因是 postinstall 会重放全部已注册 patch；即使本轮只改了一个 patch，其它已打 patch 的持久 package 也不能原样保留，否则会被二次应用。package 从根目录迁入 workspace 时还会清理已退出新注册表的旧路径；patch、注册和依赖一起删除时只清理旧路径，不要求安装恢复已经移除的 package。禁止扩大为删除整个 `node_modules`，也不新增第二次安装。
- `format`、`typecheck`、`lint` 和 server 构建不会验证 Gradle 等补丁语义。安装输出会单独扫描 `patch-package` 错误，并在安装后用只读反向检查确认每个已注册 patch 确实存在于依赖树：先用 Git 检查，遇到 patch-package 支持而 Git 默认拒绝的内部零上下文 hunk 时，再用 GNU patch 反向 dry-run 兜底；两者都失败才判未应用。npm 最终退出码成功不能掩盖 patch 失败。该 gate 同时覆盖正式重建和 `--local-branch` 临时叠加。
- 每个冲突路径都能说明相对两个父提交保留、合并或有依据地删除了什么之后，才允许执行 `continue`。

完整事故诊断见 [踩坑记录.md](踩坑记录.md#同名-patch-的-addadd-必须取语义并集)。

### 1.5 `rw-main` 组合冲突续跑

清单提交后的 rebuild 在产品目录同级 `.paseo-rw-main-operations/` 创建隔离 worktree。它先同步冻结的 `rw-base + main`，再按清单顺序合并 overlay；产品目录只在最终候选组装完成后切到独立验证分支运行一次 readiness。支持的文本冲突退出 `6`，同时打印：

```text
PASEO_RW_MAIN_OPERATION=<request>
PASEO_RW_MAIN_OPERATION_WORKTREE=<worktree>
PASEO_PREFLIGHT_STATUS=integration-conflict
PASEO_RW_MAIN_CONFLICT_PHASE=sync|overlay
```

查看状态或放弃现场：

```bash
bash "$paseo_chore_root/dwyanewang/rebuild-rw-main.sh" \
  --build-root "$paseo_build_root" --operation-status "$paseo_rw_main_operation"

bash "$paseo_chore_root/dwyanewang/rebuild-rw-main.sh" \
  --build-root "$paseo_build_root" --abort-operation "$paseo_rw_main_operation"
```

解决时只修改打印出的冲突路径并完成 `git add`。随后运行 `git write-tree`，把结果填入 operation 目录 `conflict-review.tsv` 的 `resolution-tree` 行，并为该行、双父行及每条上游提交行填写非空保留/替代说明；任何 `TODO`、空说明、缺失生成行或与当前 staged tree 不同的 tree 都会拒绝续跑。不要手工 commit、rebase、reset 或移动 operation HEAD。自动 clean merge 会在执行 Git merge 前持久化冻结的双方父提交和提交说明，得到 clean index 后再原子补记由固定双父重建核对的预期 tree；无论中断发生在 tree 补记前还是 commit 后、完成记录首次写入前，续跑都只在 merge state、父链与 tree 精确匹配时继续。某个冻结 overlay head 已包含在当前合法前缀（包括已在 rw-base 中）时，记录为该步骤的合法 no-op 并推进索引，不制造空提交；最终无变化判断也按同样的包含关系核对。普通打包原样使用同一 `--run-id --no-fetch` 重跑 prepare；lifecycle 始终运行父 request 的 `continue --operation`，包括 refs 已发布但 ready state 写入失败后的补写。多个冲突会逐个暂停，已完成前缀不会重做。

受管 merge 先以命令级 `rerere.enabled=false` 保存原 index 和 `AUTO_MERGE`，再显式以 `rerere.enabled=true,rerere.autoupdate=false` 尝试恢复内容；匹配后仍须审查和暂存。仓库未声明 rerere 意图时，首次受管 rebuild 将仓库默认写为 `false`，防止其它 worktree 因共享 rr-cache 隐式启用；已有显式 `true` 会保留并报告，受管命令仍使用命令级隔离。错误匹配应在当前冲突中纠正后再暂存，续跑会只替换当前冲突的旧记录，不能清空整个共享 rr-cache。相同分支/路径冲突从第二次起会输出不阻断的回源维护建议和确定性计数，不会自动 rebase 或 push 源分支。

验证失败保留 operation 和日志；环境修复后原样重跑会验证同一候选。候选测试在 readiness 构建和检查完成之后运行。冲突候选只枚举真实冲突快照，选择精确同名的直接回归及 posix/windows-shell 变体，以及源/上游区间内实际修改过的同名相关扩展测试；依赖区间也按变化源文件或对应源文件筛选测试。不无条件扩展到所有同前缀邻近测试，排除 e2e/browser/real/local 类型并记录覆盖缺口。路径规范化、去重后按 workspace 配置执行，app 指定 `--project unit`；每批最多 8 个，完整执行选定集合。

所有候选测试 runner 和批次使用 `LC_ALL=C LANG=C LANGUAGE=C`，并将该环境写入 `capability-tests.tsv`，纳入 PASS 复用输入。作用域仅限候选能力检查，不修改机器 locale、共享 Git 配置或 readiness 的调用环境。

适用集合超过 32 个时，脚本在原 operation 中生成 `capability-test-selection.tsv`，记录 `candidate-tree`、`applicable-set` 哈希和每个 `test` 行。逐项将 `TODO` 改成 `run|skip` 及审查依据，直接回归必须 `run`，然后原样重试。脚本拒绝缺行、重复行、未知路径、过期 tree/集合和无依据取舍。32 是自动选择门槛；逐项审查后可以保留更多必要回归，仍分批运行，无需 abort、回源或重做冲突解决。被取舍、平台不适用和没有相关测试的情况均记录覆盖缺口，不记作通过。

`capability-tests.tsv` 记录路径、选择依据、workspace、批次、平台、Node/npm、工具链、依赖、readiness 构建后的 dist 和执行器摘要。导入或 require `node:test` 的文件、`packages/cli/tests/` 的脚本测试和非 Vitest 扩展名只记录覆盖缺口，不交给 Vitest。app 接受 `src/` 下的 unit ts/tsx 测试及产品配置显式包含的 `native-release-version.test.ts`，其他范围仍记录缺口。PASS 只在全部输入及取舍相同时复用；测试失败可复用 readiness，不能复用能力结果。发布恢复中测试失败必须保留原发布进度和标志，不能因失败重新允许 abort。测试结束后再次确认候选洁净，测试留下修改时不记 PASS、不发布。冲突续跑先完成可重入的证据归档，再推进合并进度，防止中断后漏掉前序冲突的测试。lifecycle 的 sync、feature、replay 冲突分别用同步前基线、冻结功能 head、原重放提交到 main 的区间生成必填上游证据，不能用 maintain 绕过这道检查。未支持类型的冲突即使原样重试也保持失败，不转换成 exit 6。

发布使用冻结租约的远端 atomic push，再完成本地 refs；远端已成功而本地尚未完成时按真实 refs 恢复，不宣称本地与远端是一个原子事务。operation 会保留到调用方成功写入 ready state；进入 `publishing` 或 `awaiting-ready` 后普通 `--abort-operation` 会拒绝，必须恢复完成；`--confirm-operation` 仅供 prepare/lifecycle 内部确认后清理，不能人工用它绕过 ready 写入。父 lifecycle 有活动子 operation 时必须先 abort 尚未发布的子 operation，再 abort 父 operation；已经发布的 operation 不允许伪装成 abort，只能恢复完成。

### 1.6 校验次数与上游 Git hook

一次 `rebuild-rw-main.sh` 先完成 `rw-base + main + 全部 overlays`，只对最终候选运行一次完整 readiness。若整次用户请求出现多组 `format:check + typecheck + lint`，说明启动了多次 rebuild/lifecycle，而不是 5 条清单分支加 `rw-base` 各自校验。首先查是否误判未受管提交、重复发起 lifecycle，或在 lifecycle 成功后又多跑了一次 prepare；不要把多轮误编排解释为上游要求每层校验。

上游仓库规则确实要求修改后运行 typecheck/lint，`lefthook.yml` 的 pre-commit typecheck 也没有路径过滤，即使只提交文档仍会运行。控制面准备提交时，先做定向测试、`npm run format` 和一次 lint，再让 pre-commit hook 承担该轮唯一一次全仓 typecheck；不要在提交前手工 typecheck 后紧接着让 hook 重复。若本轮不提交或 hook 没有执行，才显式运行 `npm run typecheck`。

## 2. 正式产物链、临时本地叠加与端选择

readiness 成功后先为本次 attempt 确定一个新的绝对目录，并显式传入 `--run-dir`；不要把请求目录本身复用为 attempt 目录。先 source 状态 helper，用 `paseo_prepare_artifact_run_dir` 原子创建目录和 `starting` 标记，再用 `setsid ... >launcher.log 2>&1 < /dev/null &` 脱离终端启动，随后立即调用 wait helper；不要先以前台命令运行到结束再调用 helper。Codex 没有 Claude 风格的后台构建完成通知，启动 agent 通过 Paseo MCP 创建全局 heartbeat（约每 5 分钟、3 小时过期），再把 opaque ID 作为 `--heartbeat-id` 传给脚本，作为外部唤醒保障。脚本不调用需要 daemon 密码的 heartbeat CLI；没有预创建 ID 时构建仍继续，但记录 `heartbeat status=unavailable` 并打印人工检查提示。heartbeat prompt 包含绝对 run 目录、请求/attempt、说明后台 PID 会写入 `pid.env` 并按该文件恢复、终态判据和“禁止重新启动构建”；创建 heartbeat 时尚不知道真实后台 PID。等待使用低输出 helper：每 15–30 秒检查机器可读状态，仅阶段变化、终态或最长约 10 分钟静默时输出，不让代理持续 `write_stdin` 轮询。启动 agent 先调用 agent-scoped MCP `create_heartbeat`（`cron="*/5 * * * *"`、`expiresIn="3h"`），将返回的 `id` 保存到 `paseo_heartbeat_id`，再启动下面的脚本。构建进入终态后，由同一 agent 调用 MCP `delete_heartbeat({ id: paseo_heartbeat_id })`，最后执行 `PASEO_ARTIFACT_HEARTBEAT_DELETE_CONFIRMED=1 paseo_cleanup_artifact_heartbeat "$paseo_artifact_run_dir"` 将 `heartbeat.env` 从 `created` 标记为 `cleaned`。

```bash
paseo_artifact_run_dir="$paseo_build_root/.dev/build-paseo-runs/$paseo_run_id/artifact-attempt-1"
source "$paseo_chore_root/dwyanewang/build-paseo-state.sh"
paseo_prepare_artifact_run_dir "$paseo_artifact_run_dir" 60
setsid bash "$paseo_chore_root/dwyanewang/build-paseo-artifacts.sh" \
  --build-root "$paseo_build_root" \
  --preflight-state "$paseo_preflight_state" \
  --run-dir "$paseo_artifact_run_dir" \
  --heartbeat-id "$paseo_heartbeat_id" \
  >"$paseo_artifact_run_dir/launcher.log" 2>&1 < /dev/null &
paseo_artifact_launcher_pid=$!
printf '%s\n' "$paseo_artifact_launcher_pid" >"$paseo_artifact_run_dir/launcher.pid"
printf 'artifact launcher pid=%s run-dir=%s\n' "$paseo_artifact_launcher_pid" "$paseo_artifact_run_dir"
paseo_wait_for_artifact_run "$paseo_artifact_run_dir" 20 60
```

`launcher.pid` 和 `$!` 只记录脱离终端的启动进程，不能作为成功信号；构建脚本会写入包含启动时间和命令的 `pid.env`，恢复时用它防止 PID 复用。最终状态只认同一 run-dir 中原子写入的 `exit-status`、`result.env` 和目录匹配；成功必须是 `exit-status=0` 且 `result.env` 为 `ready`。`starting` 窗口结束后仍没有有效编排 PID 或终态时报告 `abandoned`，不会无限报告 `running`。
用户明确要求“不拉取/不同步”时跳过第 1 节，改用：

```bash
paseo_artifact_run_dir="$paseo_build_root/.dev/build-paseo-runs/standalone-attempt-1"
source "$paseo_chore_root/dwyanewang/build-paseo-state.sh"
paseo_prepare_artifact_run_dir "$paseo_artifact_run_dir" 60
setsid bash "$paseo_chore_root/dwyanewang/build-paseo-artifacts.sh" \
  --build-root "$paseo_build_root" \
  --skip-preflight \
  --run-dir "$paseo_artifact_run_dir" \
  --heartbeat-id "$paseo_heartbeat_id" \
  >"$paseo_artifact_run_dir/launcher.log" 2>&1 < /dev/null &
paseo_artifact_launcher_pid=$!
printf '%s\n' "$paseo_artifact_launcher_pid" >"$paseo_artifact_run_dir/launcher.pid"
paseo_wait_for_artifact_run "$paseo_artifact_run_dir" 20 60
```

若还要临时测试一个或多个本地分支，在同一条命令追加可重复的 `--local-branch`：

```bash
paseo_artifact_run_dir="$paseo_build_root/.dev/build-paseo-runs/local-windows-attempt-1"
source "$paseo_chore_root/dwyanewang/build-paseo-state.sh"
paseo_prepare_artifact_run_dir "$paseo_artifact_run_dir" 60
setsid bash "$paseo_chore_root/dwyanewang/build-paseo-artifacts.sh" \
  --build-root "$paseo_build_root" \
  --skip-preflight \
  --local-branch fix/electron-explorer-tab-menu \
  --target windows \
  --run-dir "$paseo_artifact_run_dir" \
  --heartbeat-id "$paseo_heartbeat_id" \
  >"$paseo_artifact_run_dir/launcher.log" 2>&1 < /dev/null &
paseo_artifact_launcher_pid=$!
printf '%s\n' "$paseo_artifact_launcher_pid" >"$paseo_artifact_run_dir/launcher.pid"
paseo_wait_for_artifact_run "$paseo_artifact_run_dir" 20 60
```

`--local-branch` 仅与 `--skip-preflight` 同用。脚本不 fetch，不读取远端最新状态，也不修改持久清单；它冻结显式分支的本地 SHA，从当前 `rw-main` 建立 `rw-local-build-*` 候选，合并后刷新声明并运行 format/typecheck/lint。源分支若有 worktree 必须洁净。普通退出、构建失败、INT 或 TERM 都由 trap 恢复 `rw-main` 并删除候选。

端选择使用可重复的 `--target`：

| 参数               | 行为                                                         |
| ------------------ | ------------------------------------------------------------ |
| 未传 `--target`    | 保持原有三端：server + Android + Windows                     |
| `--target server`  | 只交付服务端；不准备 app、画像或下载服务                     |
| `--target android` | 构建 app 依赖和 Android 两段；跳过 server/CLI 交付与 Windows |
| `--target windows` | 构建桌面包所需 server/CLI 依赖和 Windows zip；跳过 Android   |
| 重复多个 target    | 构建所选并集；`desktop` 是 `windows` 别名                    |

正常完整同步绝不使用 `--skip-preflight`。其它可选参数：`--download-port <端口>`、`--download-ttl <秒>`、`--no-serve-dist`；默认端口 8800、存活 10800 秒，明确拒绝 6767。

脚本负责且必须保持以下语义：

- 在删除所选旧产物前验证 ready state、`rw-base`/`rw-main` HEAD、两个 worktree 洁净度；跳过同步模式验证当前 checkout。本地叠加模式还冻结每条测试分支 SHA。
- 与 preflight 共享构建目录中的非阻塞独占锁；另一段 preflight 或产物链已运行时立即拒绝，不能让多个代理共享 refs、产物和清理状态。
- 构建前只精确删除本轮所选 APK/当前版本 zip 并把目标写入构建标记；Windows zip 成功校验后，按文件 mtime 保留当前包和最近两个历史 `Paseo-Setup-*-x64.zip`，其余旧 zip 删除。`builder-debug.yml`、`win-unpacked/` 和其它架构/格式不参与轮转。仅 app 目标重生成 terminal-webview，成功或失败均用 EXIT trap 还原。
- server 或 Windows 目标构建并验证 server、CLI、protocol；Android-only 只构建 app 依赖。
- 选中 Android 时，每次 prebuild 后应用 8 个 Metro worker 与 `local-balanced` Hermes；先用单 worker 跑完并验证 Metro/Hermes，再启动 8-worker ARM64 Native 第二段并验证 bundle producer 精确 `UP-TO-DATE`。
- 同时选中 Android 与 Windows 时，Windows 仍受 Android bundle gate 保护；gate 后 `MemAvailable` 至少 16 GiB 则并发，否则串行。Windows-only 不启动 Android，直接运行完整画像链。
- 已选 Android/Windows 使用 cgroup 画像。并发分支失败时终止并等待兄弟进程组，保留隔离日志和真实失败码；只有全部所选目标成功后才进入最终清理与发布。
- 校验新产物、还原 terminal-webview、确认两个 worktree 洁净，再启动下载服务。任何失败保留真实退出码且不生成成功结果文件。

## 3. 结果与校验

请求目录为 `$paseo_build_root/.dev/build-paseo-runs/$paseo_run_id/`，从首次 prepare 开始保留，失败不会删除。它不只是日志，也保存恢复和产物关联所需状态；完成或明确放弃前，任何日志轮转/清理都不得裁剪该目录：

- `requested-at`：消息起点（未提供 `--requested-at` 时为首次命令时间）。
- `main.snapshot`：本轮 main SHA 和同步时间；不是 ready 凭证。
- `main.refreshes`：追加式 main 代次审计，每行 `<sha> <epoch> initial|refresh`；`main.snapshot` 仍只保留当前代次的一行契约。
- `preflight-<时间>-<PID>.log`：各次准备命令的完整 stdout/stderr。
- `preflight-stages.log`：追加式阶段记录，含每次尝试、同步、GraphQL、合并预检、依赖安装、声明构建、format/typecheck/lint、缓存命中及真实退出码。审查、修复、提交的开始/结束由主代理追加事件，例如：

```bash
PASEO_BUILD_REQUEST_STAGE_LOG="$paseo_build_root/.dev/build-paseo-runs/$paseo_run_id/preflight-stages.log" \
  bash -c 'source "$1"; paseo_build_stage "$2"' _ \
  "$paseo_chore_root/dwyanewang/build-paseo-state.sh" 'review:start'
```

事件使用 `review:start/end`、`source-repair:start/end`、`manifest-commit:start/end`；不把空白时间擅自归为机器或代理耗时。`PASEO_BUILD_REQUEST_STAGE_LOG` 是请求事件的输入路径；产物链打印的 `PASEO_BUILD_STAGE_LOG` 仅指向独立 attempt 的 `stages.log`，两者不能互换。正式产物的 attempt 路径自动写入请求的 `artifacts:start` 事件，后续产物阶段与结束状态也追加到同一请求日志。ready state 失败失效与历史日志保留是两个独立机制。

每次正式产物 attempt 目录的文件：

| 文件             | 含义                                                                     |
| ---------------- | ------------------------------------------------------------------------ |
| `build.log`      | 完整产物链输出                                                           |
| `stages.log`     | 带时间戳的阶段切换                                                       |
| `*.branch.log`   | 已选择的 Android Native / Windows 分支隔离输出                           |
| `exit-status`    | 真实退出码，成功或失败均原子写入；缺失时结合 PID 文件判断运行中/异常中断 |
| `result.env`     | 仅成功时原子生成；必须与同一 run 目录、`exit-status=0` 一起才算成功      |
| `pid.env`        | 编排 PID、进程启动时间和命令；用于避免 PID 复用导致的误报                |
| `heartbeat.env`  | heartbeat ID 与清理状态；异常退出后由同一 agent 身份恢复清理             |
| `terminal-state` | 终态收尾幂等标记；只证明脚本已写完状态，不代表代理已向用户汇报           |

所选目标的固定产物：

| 端      | 路径                                                                                    |
| ------- | --------------------------------------------------------------------------------------- |
| 服务端  | `packages/server/dist/server/server/exports.js`，CLI 为 `packages/cli/dist/index.js`    |
| Android | `packages/app/android/app/build/outputs/apk/release/app-release.apk`                    |
| Windows | `packages/desktop/release/Paseo-Setup-<版本>-x64.zip`；目录中同类 zip 最多保留 3 个版本 |

先核对 `paseo_artifact_targets` 和 `paseo_artifact_preflight_mode`。本地叠加模式还要核对 `paseo_artifact_local_overlay_count` 及每条 branch/head。Windows 目标还要核对 `paseo_artifact_windows_retention_limit=3`、`paseo_artifact_windows_archive_count` 和 `paseo_artifact_windows_pruned_count`。已选 Android 的两份和已选 Windows 的一份 summary 必须是 `exit_status=0`，汇报 `command_wall_seconds`、`average_cpu_cores`、`peak_sampled_cpu_cores`、`host_cpu_percent`、`memory_peak_bytes`、`swap_peak_bytes`、`minimum_host_mem_available_bytes`；不要用含采样收尾的 `service_runtime` 代替阶段墙钟。`paseo_artifact_parallel_mode` 还可能是 `android-only`、`windows-only` 或 `not-applicable`。

### 3.1 Expo modules 预检、失败与恢复

选择 Android 或 Windows 时，产物删除和 `prepare-build` 之前会按 Expo 实际 resolver 扫描 `packages/app/modules`：可见的直接目录，以及可见 scoped 目录（`@scope/name`）下的子目录和符号链接。每个候选都必须有可解析的 `package.json`，并且 `git ls-files -- <dir>` 非空；不要求 Android 目录或 `expo-module.config.json`，所以纯 RN/iOS-only 模块仍合法。若配置出现 `nativeModulesDir`，预检会明确失败并要求先更新规则。

只剩 ignored build 残留、缺失或损坏 `package.json` 的模块会打印模块路径、tracked/ignored 状态、可识别的 name/version 和隔离建议；脚本不会自动删除或移动它们。预检失败发生在 `prepare-build` 之前，因此不会先删除旧 APK/ZIP。low-memory 只是一条阶段状态（可回退串行），不是失败。

同一请求如果已经存在成功 attempt，恢复或上下文压缩后的重入只读汇报该 attempt，不再重复 `prepare-build`、删除产物或重启构建。缺失 `exit-status` 的 run 仅在 PID 启动时间和命令均匹配、编排进程仍存活时报告 `running`；进程已退出报告 `abandoned` 并给出最后阶段，绝不永久报告 running。失败、异常中断和取消都保留 run 目录、日志及机器可读状态；取消只发送安全 SIGTERM，不使用 `kill -9`。`terminal-state` 只表示脚本完成终态收尾，不表示代理已经向用户汇报；消费方必须在确认后自行记录汇报。heartbeat ID 持久化在 `heartbeat.env`。异常退出或终态后，恢复 agent 先用同一身份通过 MCP 删除 heartbeat，再执行 `source dwyanewang/build-paseo-state.sh; PASEO_ARTIFACT_HEARTBEAT_DELETE_CONFIRMED=1 paseo_cleanup_artifact_heartbeat <run-dir>` 标记 `cleaned`；没有身份或 MCP 删除失败时不要伪造 cleaned，只保留到自动过期。成功后按幂等顺序清理 heartbeat，并只发送一次最终结果。

## 4. 下载服务与交付

产物脚本会为已选 Android/Windows 目标启动下载服务并只暴露本轮目标；server-only 自动不启服务。地址使用脚本打印的实际 LAN/Tailscale 值，不要写死 VM IP。Tailscale 未登录只会少一个地址，不是构建失败。需要刷新或提前停止时从控制面运行：

```bash
bash "$paseo_chore_root/dwyanewang/serve-dist.sh" keep
bash "$paseo_chore_root/dwyanewang/serve-dist.sh" stop
```

`keep` 从本轮构建标记恢复目标，只刷新所选产物且不重置原 TTL；也可显式传 `--target android|windows`，但必须与标记一致。`stop` 只停止状态文件中身份匹配的自有服务。未知端口占用时报告，不杀其他进程。

最终汇报：本轮 main 快照 SHA/同步时间、持久清单增删及提交（若有）、临时本地分支及冻结 SHA（若有）、所选产物路径/体积/mtime、Windows 历史 zip 保留/清理数量、已选端资源数据、适用时的并发/回退模式、下载地址和真实总墙钟。ready-state 产物结果的 `paseo_build_request_id/dir` 关联原请求，`paseo_build_snapshot_main` / `paseo_build_frozen_at` 记录快照，`paseo_build_request_total_seconds` 从提供的消息时间计至下载服务就绪；缺少消息时间或旧 ready state 时须说明实际起点。`paseo_artifact_total_seconds` 只代表正式产物链，不能扣除阅读、审查、冲突修复或失败重试。
