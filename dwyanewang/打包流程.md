## 1. 拉取最新代码（同步上游 → 可重建地生成 rw-main）

> **可跳过（自测常用）**：若用户明确表示"不拉取最新代码""不同步上游代码"（或"不更新代码""用当前代码打包"等同义表达），**整节跳过**，直接从第 1.5 节（重生成 terminal-webview）开始，用当前工作区代码打包。该模式不会自动增删 `rw-main-branches.txt`；“新增 PR/分支”和“不同步”不能同时使用。

> 本仓库是 `getpaseo/paseo` 的 fork。`main` 是上游的**干净镜像**（绝不直接在 main 上提交），`chore/build-paseo` 保存构建控制资产，`rw-main` 是可重建的个人发行分支。
> remote：`origin` = `git@github.com:dwyanewang/paseo.git`（fork，SSH 免密）；`upstream` = `https://github.com/getpaseo/paseo.git`（源仓库，fetch-only）。
> `chore/build-paseo` 是唯一构建控制面，保存清单、技能、脚本和文档，但**不合并进产品分支**。`rw-main` 只由 `main` 和 [`rw-main-branches.txt`](rw-main-branches.txt) 中仍需提前使用的功能分支整体生成。**不要再把 chore、main 或 rebase 后的 PR 分支追加合并到旧 rw-main**；这会污染产品历史并累积重复 merge。

**固定 worktree 拓扑**

- `/home/yangfei/Projects/paseo` 是专用构建 worktree，正常应停留在 `rw-main` 并保留 Android/Gradle/Electron 缓存。若开始时是其他分支，只要工作区干净且不是 detached HEAD，重建脚本会自动切入并在成功后停留于 `rw-main`；有改动则停止，不 stash、不覆盖。
- `chore/build-paseo` 位于独立 worktree，专门维护控制面；清单内每个功能分支也使用独立 worktree。控制面脚本通过必填的 `--build-root` 明确操作专用构建目录，不依赖调用者当前目录。
- worktree 共享 Git refs，但源码、`dist`、`node_modules` 和构建缓存相互隔离。不要手工在构建目录来回切换分支；若确实从其他分支启动完整流程，由重建脚本统一切换并先对齐依赖。

```bash
paseo_build_root=/home/yangfei/Projects/paseo
paseo_chore_root=$(git worktree list --porcelain | awk '
  /^worktree / { path = substr($0, 10) }
  $0 == "branch refs/heads/chore/build-paseo" { print path }
')
[[ -n "$paseo_chore_root" ]]
[[ -z "$(git -C "$paseo_build_root" status --porcelain)" ]]
[[ -n "$(git -C "$paseo_build_root" branch --show-current)" ]]
[[ "$(git -C "$paseo_chore_root" branch --show-current)" == chore/build-paseo ]]
[[ -z "$(git -C "$paseo_chore_root" status --porcelain)" ]]

# 1.1 获取远端并安全快进本地 main；若 main 已签出，必须同步其 worktree
git -C "$paseo_chore_root" fetch upstream
git -C "$paseo_chore_root" fetch origin --prune
paseo_main_worktree=$(git -C "$paseo_chore_root" worktree list --porcelain | awk '
  /^worktree / { path = substr($0, 10) }
  $0 == "branch refs/heads/main" { print path }
')
if [[ -n "$paseo_main_worktree" ]]; then
  [[ -z "$(git -C "$paseo_main_worktree" status --porcelain)" ]]
  git -C "$paseo_main_worktree" merge --ff-only upstream/main
else
  git -C "$paseo_chore_root" merge-base --is-ancestor main upstream/main
  git -C "$paseo_chore_root" branch -f main upstream/main
fi
git -C "$paseo_chore_root" push origin main:main       # origin/main ← main ← upstream/main

# 1.2 在 chore worktree 自动维护清单（用户指定新增项时放进 sync_args）
sync_args=()
# sync_args+=(--add-pr 2345)
# sync_args+=(--add-branch feat/example)
sync_status=0
( cd "$paseo_chore_root" && \
  bash dwyanewang/sync-rw-main-branches.sh "${sync_args[@]}" ) || sync_status=$?

if ((sync_status == 3)); then
  # 强制语义审查：逐项浏览报告中的 main/head 区间及变更路径。
  # 对可能覆盖相同用户能力的提交继续查看 PR 说明和完整 diff，并逐项与清单功能比较。
  review_removals=()
  # 明确完整吸收时添加：review_removals+=(--remove-branch feat/example)
  # 部分吸收时先 rebase/修整源功能分支并验证、推送，然后从本步骤重新开始。
  # 结论不明确时询问用户；不得执行下面的确认命令。
  current_main=$(git -C "$paseo_chore_root" rev-parse main)
  ( cd "$paseo_chore_root" && \
    bash dwyanewang/sync-rw-main-branches.sh \
      "${sync_args[@]}" "${review_removals[@]}" \
      --accept-main-review "$current_main" )
elif ((sync_status != 0)); then
  exit "$sync_status"
fi

# 仅当上一步实际修改了清单时执行；一次同步中的全部增删只产生一个提交
if ! git -C "$paseo_chore_root" diff --quiet -- dwyanewang/rw-main-branches.txt; then
  ( cd "$paseo_chore_root" && npm run format )
  git -C "$paseo_chore_root" diff --name-only          # 应只有 rw-main-branches.txt
  git -C "$paseo_chore_root" add dwyanewang/rw-main-branches.txt
  # 写实际审查区间，以及删除/修整项的上游提交或 PR；不得保留下面的占位文本。
  rw_main_review_summary="Reviewed main OLD_SHA..NEW_SHA; retained ...; removed ... because upstream PR #..."
  git -C "$paseo_chore_root" commit \
    -m "chore(build): sync rw-main branches" \
    -m "$rw_main_review_summary"
  git -C "$paseo_chore_root" push origin chore/build-paseo
fi

# 1.3 从控制面调用脚本，在专用构建目录原子重建个人发行分支
build_starting_branch=$(git -C "$paseo_build_root" branch --show-current)
rw_main_before=$(git -C "$paseo_build_root" rev-parse --verify rw-main 2>/dev/null || true)
bash "$paseo_chore_root/dwyanewang/rebuild-rw-main.sh" \
  --build-root "$paseo_build_root" \
  --push
rw_main_after=$(git -C "$paseo_build_root" rev-parse rw-main)
if [[ "$rw_main_before" == "$rw_main_after" ]]; then
  rw_main_rebuilt=0                         # 输入完全一致，脚本已走 no-op
else
  rw_main_rebuilt=1                         # 输入变化，已完整重建并检查
fi

dependencies_reinstalled=0
if [[ "$build_starting_branch" != rw-main ]]; then
  dependencies_reinstalled=1               # 脚本已在切入 rw-main 后无条件安装
elif ((rw_main_rebuilt)) && \
  { ! git -C "$paseo_build_root" show-ref --verify --quiet refs/heads/rw-main-backup-latest || \
    ! git -C "$paseo_build_root" diff --quiet rw-main-backup-latest..rw-main -- \
      package.json package-lock.json ':(glob)**/package.json' \
      ':(glob)patches/**' scripts/postinstall-patches.mjs; }; then
  dependencies_reinstalled=1               # 脚本已在候选检查前安装
fi
```

清单同步脚本会查询已有 `PR #编号`：仅当 PR 已合入且其 merge commit 已进入本地 `main` 时自动删除。它不会扫描并加入其他开放 PR；新增项必须由用户明确指定：

```bash
# PR 号：自动解析 dwyanewang 的源分支，并记录 PR 元数据供日后自动删除
bash dwyanewang/sync-rw-main-branches.sh --add-pr 2345

# 无 PR 的长期个人分支
bash dwyanewang/sync-rw-main-branches.sh --add-branch feat/example

# 多项按参数顺序追加；只看差异、不落盘时加 --dry-run
bash dwyanewang/sync-rw-main-branches.sh --add-pr 2345 --add-branch feat/example --dry-run

# 完成语义审查后确认当前 main；完整吸收的分支可在同一次原子更新中删除
bash dwyanewang/sync-rw-main-branches.sh \
  --remove-branch feat/example \
  --accept-main-review "$(git rev-parse main)"
```

`--add-pr` 只接受 `getpaseo/paseo` 中归 `dwyanewang` 所有的开放 PR；两种新增方式都要求本地分支与 `origin/<分支>` 已存在且一致。GitHub 查询失败、PR 不属于当前用户或源分支未推送时，脚本在修改清单前停止。

`rw-main-branches.txt` 的每个分支项都带 `reviewed-main:<完整 SHA>` 和 `reviewed-head:<完整 SHA>`：前者是该项上次审查到的上游 main，后者是当时审查的功能分支 head。各项可以有不同基线。`main` 前进时每项检查自己的 `reviewed-main..main`；分支 head 变化时额外检查自己的 `reviewed-head..当前 head`；新分支从 `merge-base(main, branch)` 开始审查。同步脚本逐项输出全部相关提交、变更路径、PR 元数据、独有/等价补丁和路径重叠；这些 Git 事实只用于排查优先级，不能替代语义判断。未传正确的 `--accept-main-review` 时脚本不写清单并以状态 `3` 退出。

审查结果固定为四种：未吸收则保留；完整吸收则用 `--remove-branch` 删除；部分吸收则先在源功能分支 rebase 最新 `main`、删除重复部分并完成定向验证/推送，再重跑审查；结论不明确则询问用户。代理可直接处理证据明确的情况，模糊项不得自行确认。原 PR 显示已合并仍按确定性规则自动删除；仅有 patch 等价或路径重叠时绝不自动删除。确认后每个保留项的 main/head 坐标同时推进到当前引用；若自动删除后清单为空，已不存在重复风险，无需保留全局基线。

重建脚本从 chore worktree 读取清单，但所有 Git 候选、检查和切换都在 `--build-root` 指定目录执行。它在 no-op 或候选 merge 之前逐项要求 `reviewed-main` 等于当前 `main`、`reviewed-head` 等于当前功能分支 head；任一坐标缺失、重复、格式错误、提交不存在或落后都会停止，`--dry-run` 也不绕过。随后反向检查现有 `rw-main` 的产品 merge 链：每层必须恰好以清单中对应功能分支的当前 head 为第二 parent，顺序一致，最终第一 parent 必须是当前 `main`。输入完全一致时打印 `No-op:`，不重建、不重复 format/typecheck/lint；带 `--push` 时若远端不同，仍用精确的 `--force-with-lease` 同步。任一产品输入变化才按清单顺序创建临时候选，随后刷新 relay/protocol/client 声明并运行 format/typecheck/lint，全部成功后才移动 `rw-main`。

若 build root 开始时不是 `rw-main`，脚本在切入产品树后无条件运行 `npm install`；若原本已经是 `rw-main`，仅当 root/workspace package、lockfile、`patches/**` 或 `scripts/postinstall-patches.mjs` 发生变化时安装。安装发生在生成声明和仓库检查之前。失败时恢复原分支并清理临时候选；成功后固定停留于 `rw-main`。`--dry-run` 始终完整创建并验证候选，不使用 no-op。

### 1.4 readiness gate 失败时的处理

在重建通过前，**禁止启动服务端、Android 或 Windows 构建**。先按错误性质处理：

- 同一 workspace 内的源码 import 报“没有导出的成员”、helper 改名或参数不匹配，是分支组合不兼容，不是 `dist` 陈旧。用报错路径和 `git log --all -- <文件>` 定位源功能分支，在该分支自己的 worktree rebase 最新 `main`、修正并验证。
- 只有错误实际跨 workspace 指向生成声明（如 client 读取 `packages/relay/dist/*.d.ts`）时，才重建声明拥有方：protocol/client 用 `npm run build:client`，server/CLI 或 relay 链用 `npm run build:server`。
- 功能分支修复后运行 `npm run format`、`npm run typecheck`、`npm run lint` 和相关的单个测试。app Playwright 定向测试必须清空外部主 daemon 密码：

  ```bash
  PASEO_PASSWORD= npm run test:e2e --workspace=@getpaseo/app -- \
    e2e/new-workspace-dictation-submit.spec.ts
  ```

  `.env.test` 未声明 `PASEO_PASSWORD` 不代表变量为空：dotenv 默认不会删除父进程已经存在的值。

- rebase 后用 `git push --force-with-lease origin <功能分支>`，然后回到固定主目录重新运行原子重建。不要在临时候选或 `rw-main` 上直接修补产品源码。

**PR 分支生命周期**

- PR 分支可以暂时落后 `main`；重建时脚本会打印 ahead/behind，并通过三方合并验证组合。
- `main` 前进后，每个分支必须从自己的 `reviewed-main` 审查到当前 main；分支 head 变化时即使 main 不变也必须从自己的 `reviewed-head` 重新审查。上游用另一 PR、直接提交或不同架构实现同一功能时，不以原 PR 状态作为保留依据。
- PR 分支 rebase 或增加提交后，重新运行重建脚本；不要把新提交继续 merge 到旧 `rw-main`。
- PR 被上游合入后，下一次完整同步会自动从 `rw-main-branches.txt` 删除该分支；上游最终代码由 `main` 提供，不做 revert。
- 新 PR 不会被自动发现。打包时明确说“把 PR #编号加入 rw-main 清单”，或手动向同步脚本传 `--add-pr`。
- 若重建冲突，脚本会中止并保持原 `rw-main` 不变。优先在对应 PR 分支 rebase、解决冲突并测试，再重建。

**校验**

```bash
git branch --show-current                                   # 应是 rw-main
git merge-base --is-ancestor main rw-main                   # rw-main 基于最新 main
git rev-list --left-right --count rw-main...origin/rw-main   # --push 后应为 0 0
```

> - SSH push 偶发 `Connection closed ... port 22`，**重试即可**（网络抖动，非配置问题）。
> - 提交身份固定 `dwyanewang <908280968@qq.com>`。
> - 想把合并后的 rw-main 也推回 fork：`git push origin rw-main`（打包本身不需要，按需）。
> - 若 `npm install` 报 `ENOTEMPTY` 或之后 `tsc: not found`：`rm -rf node_modules/**/.vitest-*; npm rebuild`。

## 1.5 预处理：重生成 terminal-webview（每次必做）

```bash
cd ~/Projects/paseo
bash "$paseo_chore_root/dwyanewang/serve-dist.sh" prepare-build
( cd packages/app && npm run build:terminal-webview ) # 重新生成 ~1.2MB 内联 HTML
```

`prepare-build` 从根 `package.json` 读取版本，删除且只删除该版本的目标 APK/zip，再写入本轮构建标记。后续下载服务只接受晚于该标记的两个精确产物，因此失败构建不会退回上轮 APK，也不会把“最新 zip”与旧 APK 混在一起。

`src/terminal/webview/terminal-emulator-webview-html.ts` 是 esbuild 把 xterm 打成内联 HTML 字符串的生成产物，安卓 / Windows 包都要打进它。**必须在 expo prebuild / expo export 之前重生成**，对齐 EAS 云钩子 `eas-build-post-install`（当前 = `npm --prefix ../.. run build:app-deps && npm run build:terminal-webview`）。

> 跑完 `git status` 该文件会显示 `M`——**正常**。它确定性生成但内容绑定本地构建环境，与仓库版差几行。**打包全部完成后还原它（见第 4.5 节），不要提交**。

## 2. 打包服务端

```bash
cd ~/Projects/paseo
if ((rw_main_rebuilt && !dependencies_reinstalled)); then
  # rebuild 已刷新 relay/protocol/client，只补齐其余服务端产物
  npm run build:highlight
  npm run build --workspace=@getpaseo/server
  npm run build --workspace=@getpaseo/cli
else
  # rw-main no-op、执行过 npm install 或状态不确定时走完整构建
  npm run build:server
fi
```

完整路径依次构建 highlight → relay → protocol → client → server → CLI。仅当本轮刚完成完整 `rw-main` 重建且未执行 `npm install` 时，才复用重建阶段已经生成的 relay/protocol/client 声明；不确定前序状态时一律回退到 `npm run build:server`。

**校验**（注意 server/protocol 用 `exports` 而非 `index.js`）

```bash
test -f packages/cli/dist/index.js && echo CLI_OK
ls packages/server/dist/server/server/exports.js     # server 真实入口
ls packages/protocol/dist/*.js | head                # protocol 逐文件导出
```

退出码 0 且上述文件存在即成功。

## 3. 打包安卓端 APK

```bash
cd ~/Projects/paseo/packages/app
# 3.1 生成/更新原生工程（CI=1 即非交互；expo CLI 54+ 已删 --non-interactive）
CI=1 npx cross-env APP_VARIANT=production expo prebuild --platform android

# 3.1.1 保留 Metro transform cache，让 Metro 使用 8 worker，并启用本地均衡 Hermes
bash "$paseo_chore_root/dwyanewang/configure-android-build.sh" \
  --build-root "$paseo_build_root" \
  --metro-workers 8 \
  --hermes-profile local-balanced

# 3.2.1 先单独打 Metro/Hermes bundle（Hermes 吃内存，不和原生编译并发）
cd android
paseo_resource_profile_dir="$paseo_build_root/.dev/build-profiles/$(date +%Y%m%d-%H%M%S)-$$"
bash "$paseo_chore_root/dwyanewang/profile-build-resources.sh" \
  --label android-metro-hermes \
  --output-dir "$paseo_resource_profile_dir" \
  -- ./gradlew :app:createBundleReleaseJsAndAssets \
  --no-daemon --no-parallel --max-workers=1 \
  -Dorg.gradle.jvmargs="-Xmx2g -XX:MaxMetaspaceSize=768m" \
  -PreactNativeArchitectures=arm64-v8a

# 3.2.2 确认第一段产物，再用 8 worker 编译 ARM64 原生库并封包
android_bundle_output=app/build/generated/assets/createBundleReleaseJsAndAssets/index.android.bundle
[[ -s "$android_bundle_output" ]]
bash "$paseo_chore_root/dwyanewang/profile-build-resources.sh" \
  --label android-native-assemble \
  --output-dir "$paseo_resource_profile_dir" \
  -- ./gradlew assembleRelease -x :app:createBundleReleaseJsAndAssets \
  --no-daemon --parallel --max-workers=8 \
  -Dorg.gradle.jvmargs="-Xmx4g -XX:MaxMetaspaceSize=1024m" \
  -PreactNativeArchitectures=arm64-v8a
printf 'Android resource profiles: %s\n' "$paseo_resource_profile_dir"
```

**产物**

```
~/Projects/paseo/packages/app/android/app/build/outputs/apk/release/app-release.apk   (ARM64-only)
```

**校验**

```bash
ls -lh ~/Projects/paseo/packages/app/android/app/build/outputs/apk/release/app-release.apk
# 构建日志应有 BUILD SUCCESSFUL
```

**说明**

- 两段构建是为了错开 Hermes 和 NDK 的内存峰值：Hermes 段只有一个主任务，串行不会损失可用并行度；当前构建机为 20 核 / 27 GB，原生段使用 8 worker。若后续观察到持续 swap 或 OOM，先把原生段降回 6，不要重新合并两个阶段。
- React Native 的 bundle task 会先传 `--reset-cache`；配置脚本在生成工程里追加 Expo 支持的 `--reset-cache false`，由后出现的布尔值覆盖它，并把 Metro 自己的 worker 从旧生成工程残留的 2/4 调到 8。它复用的是按内容寻址的 transform cache；源码变更后仍重新生成最终 JS bundle 并运行 Hermes，不会分发旧 bundle。
- `configure-android-build.sh` 必须在**每次** Expo prebuild 后运行；脚本幂等，并会先验证当前 Expo 参数解析和 React Native 参数顺序仍兼容。`local-balanced` 把 Hermes flags 从默认的 `-O -output-source-map` 改为 `-O`：保留正式版同级的运行时优化，只跳过本地 APK 的 Hermes Source Map 生成与合并。代价是该 APK 的 JS 崩溃堆栈不能用 Hermes Source Map 还原；Java/Kotlin 原生堆栈和 R8/ProGuard mapping 不受影响。需要排查本地 Release JS 崩溃时可临时传 `--hermes-profile production` 恢复 Source Map；正式/EAS 构建不调用此脚本，仍使用默认 production flags。Gradle 命令的 `--max-workers=1` 只控制第一段 Gradle worker，不会把 Metro 的 8 worker 降成 1。
- `-Dorg.gradle.jvmargs` 只限制 Gradle JVM，不会给 Hermes 子进程设内存上限。Hermes 已实测可达约 9.7 GB RSS，不要尝试把它“固定为 6 GB”。
- `profile-build-resources.sh` 使用 systemd transient cgroup，覆盖 Gradle 以及它启动的 Java、Node、Metro、Hermes、CMake 等全部后代，而不是只看某一个 PID 的 RSS。每段生成 `<label>.summary`、`<label>.samples.tsv`、`<label>.transcript.log` 和内部 command-result；summary 中 `command_wall_seconds` 是原命令真实耗时，`average_cpu_cores` / `host_cpu_percent` 是整组累计 CPU，`peak_sampled_cpu_cores` 是每秒采样峰值，`memory_peak_bytes` / `swap_peak_bytes` 是 cgroup 精确峰值。cgroup 内 wrapper 写出的 command-result 是命令退出码和聚合数据的权威来源；systemd 因 inotify/cgroup watch 耗尽而在收尾返回 timeout 时只设置 `systemd_cleanup_degraded=1`，清理最多等待 3 秒，不把成功构建改判为失败。`service_runtime` 仍只是可选诊断，不用于构建耗时比较。输出保存在已忽略的 `.dev/build-profiles/`，不污染 `rw-main`。
- 第二段的 `-x :app:createBundleReleaseJsAndAssets` 只允许用于同一条构建链：第一段必须刚刚成功，并且 `index.android.bundle` 非空。它避免环境差异或恢复执行使 Gradle 再跑一次全量 Hermes；若单独从 native assemble 开始，必须先补跑第一段，不能拿未知旧 bundle 直接排除任务。
- 个人自用包固定 `arm64-v8a`，减少约四分之三的多 ABI 原生编译。若以后需要通用分发，把两处参数改为 `-PreactNativeArchitectures=armeabi-v7a,arm64-v8a,x86,x86_64`。
- **不要清理** Metro / Gradle 缓存、`.cxx` 或各模块 `build/`，否则下次会重做 JS transform 或原生编译。
- release 包用 debug keystore 签名，自测够用，不能上架商店。
- 装到手机：`adb install -r <apk路径>`（手机开 USB 调试），或手动拷贝安装（允许未知来源）。

## 4.5 收尾：还原 terminal-webview（保持工作区干净）

三端全部打完后，把第 1.5 节重生成导致 `M` 的那个文件还原成仓库版：

```bash
cd ~/Projects/paseo
git restore --worktree -- packages/app/src/terminal/webview/terminal-emulator-webview-html.ts
```

**为什么还原而不是提交**（2026-06 多轮验证后定的）：

- 它是被 vendoring 进仓库的**构建产物**，被 `terminal-emulator.native.tsx` import（不能 gitignore），打包前必须重生成、于是必然 `M`。
- 想提交进 rw-main 会被 pre-commit 的 `oxfmt --check`（lefthook format 步骤）拦——生成脚本输出未格式化、仓库版是格式化过的；绕过去要么 `--no-verify` 塞未格式化文件、要么给打包再加 format 步骤，都不如还原干净。
- CI 不校验它最新，EAS 云构建和本地打包都现场重生成，仓库版是否最新对任何构建都无影响 → 提交零收益。
- 还原零副作用：工作区回到仓库版、不污染历史、不和 main/upstream 分叉。

> rw-main 是个人分支、不推 upstream（同步走 main），所以这文件 `M` 本身无害；还原只是图工作区干净。

  exit 1

restore_terminal_webview() {

trap restore_terminal_webview EXIT

paseo_main_worktree=$(git -C "$paseo_chore_root" worktree list --porcelain | awk '

## 5. 传输到物理机（172.16.21.200，Win11）

**网络拓扑**：本机是 VM（网卡 IP `172.18.6.118`），物理机是 `172.16.21.200`。
经测试：**VM 出站受限 → ping 不通物理机；但物理机能访问 VM 的 `172.18.6.118`**。
因此传输方向只能是 **物理机主动来拉**：VM 起 HTTP 服务，物理机用浏览器下载。

> ⚠️ 不要尝试从 VM 用 scp/smb 主动推送到物理机——VM 出站不通，会失败。

### 5.1 一键起服务（推荐，存活 3 小时自动清理）

**打包成功后**运行同目录脚本 [`serve-dist.sh`](serve-dist.sh)，它会汇集 APK+zip、起 HTTP 服务、并用 `timeout` 控制 **3 小时后自动停服并删除 staging 目录**：

```bash
bash "$paseo_chore_root/dwyanewang/serve-dist.sh"            # 端口 8800，刷新文件并(重新)计时 3 小时
bash "$paseo_chore_root/dwyanewang/serve-dist.sh" 8800 10800 # 自定义 端口 存活秒数
bash "$paseo_chore_root/dwyanewang/serve-dist.sh" keep       # 沿用在跑的服务、只刷新文件，不重置计时
bash "$paseo_chore_root/dwyanewang/serve-dist.sh" stop       # 提前手动停服 + 清理
```

脚本输出会打印物理机访问地址（自动探测 VM IP）。要点：

- **幂等自愈**：3 小时内再次打包后重跑脚本，默认会停掉旧服务、用最新产物重起、**计时重置为 3 小时**（不会端口冲突）。想保留原计时只刷新文件用 `keep`。
- 用 `setsid` 脱离会话，**跨 session 存活**（关掉 Claude 会话也不影响）。
- 3 小时由 `timeout 10800` 控制，到点自动停止并清理构建 worktree 下的 `.dev/serve-dist/dist`。
- 版本号从根 `package.json` 读取并保留 prerelease 后缀；只接受 `prepare-build` 之后生成的固定 APK 和精确版本 zip，不再按 mtime 猜“最新 zip”。
- `PORT`/`TTL` 必须是范围内数字，端口 `6767` 被明确拒绝。脚本只停止状态文件中记录且命令身份匹配的自有进程；若目标端口被其他服务占用，只报错，不杀进程。
- **Tailscale 私有直连（可选）**：脚本会优先探测主机原生 Tailscale；没有原生客户端时，复用已授权的 `paseo-tailscale-download` Docker 容器，容器停止会自动启动。就绪时会额外打印 `http://<Tailnet-IP>:8800/`，手机/Windows 登录同一 Tailnet 后可直接下载；未就绪不会影响局域网服务或让打包失败。
- 首次 Tailscale 安装与网页登录必须在打包前单独完成；不要启用 Funnel、Exit Node 或子网路由。安卓下载时 Tailscale 和 Clash 的 VPN/TUN 模式不能同时启用。

### 5.2 在物理机（Win11）上下载

浏览器打开（实测此地址可达，端口默认 8800）：

```
http://172.18.6.118:8800/
```

点击下载两个文件即可。

> 若打不开：在物理机 PowerShell 跑 `Test-NetConnection 172.18.6.118 -Port 8800` 看是否通；
> VM 的 IP 可能随环境变化，以脚本输出的地址为准（脚本会自动探测并打印）。

### 5.3 提前停服（可选，否则 3h 自动清理）

```bash
bash "$paseo_chore_root/dwyanewang/serve-dist.sh" stop
```

> `stop` 只处理脚本自己的状态文件，不接受端口参数；状态缺失或身份不匹配时不会触碰任何进程。
