# Paseo 本地产物打包流程

> 目标：在 Ubuntu 按需构建服务端、Android ARM64 APK 和 Windows x64 zip，并为所选可下载产物启动临时下载服务。
> 版本以根 `package.json` 为准。打包只使用下述版本化入口，不再由代理复制各阶段命令。

## 0. 固定环境与 worktree

- 产品构建目录：`/home/yangfei/Projects/paseo`，正常停留在 `rw-main`，长期保留 Android/Gradle/Metro/NDK/Electron 缓存。
- 控制面：独立的 `chore/build-paseo` worktree，只保存 `dwyanewang/` 下的清单、脚本和文档，不合并进产品分支。
- `main` 始终镜像 `upstream/main`；`rw-base` 以追加历史保存长期本地功能；`rw-main` 由 `rw-base` 和 [`rw-main-branches.txt`](rw-main-branches.txt) 中的临时叠加分支按顺序重建。
- 不直接在 `rw-base` 或 `rw-main` 修改产品代码。长期功能只通过 `manage-rw-base.sh promote|maintain` 进入基线；临时上游候选才进入叠加清单。
- 不拉取代码的测试构建可以在同一把构建锁内创建 `rw-local-build-*` 临时候选并叠加显式本地分支。该候选不写清单、不移动 `rw-main`、不推送，构建成功或失败后都恢复产品 worktree。
- worktree 共享 Git refs，但源码、`node_modules`、`dist` 和构建缓存独立。任何相关 worktree 有改动或 detached HEAD 时停止，不 stash、不覆盖。
- 工具版本来自 `.tool-versions` / `.mise.toml`；脚本会在自己的 shell 中安装并激活 mise。Wine 只使用 `~/.local/share/paseo/wineprefix`，绝不删除默认 `~/.wine`。
- 禁止重启或触碰 6767 主 daemon。

先定位控制面：

```bash
paseo_build_root=/home/yangfei/Projects/paseo
paseo_chore_root=$(git worktree list --porcelain | awk '
  /^worktree / { path = substr($0, 10) }
  $0 == "branch refs/heads/chore/build-paseo" { print path }
')
[[ -n "$paseo_chore_root" ]]
```

## 1. 完整同步与 readiness gate

除非用户明确要求“不拉取/不同步”，每次从控制面单次调用：

```bash
paseo_preflight_state="$paseo_build_root/.dev/build-paseo-preflight.env"
bash "$paseo_chore_root/dwyanewang/prepare-rw-main-for-build.sh" \
  --build-root "$paseo_build_root" \
  --state-file "$paseo_preflight_state" \
  --push
```

用户明确要求新增项时，在同一命令末尾按用户给出的顺序追加：

```bash
--add-pr 2345
--add-branch feat/example
```

新 PR 不自动发现。`--add-pr` 只接受 `dwyanewang` 拥有的上游 PR 并自动解析源分支；`--add-branch` 只用于需要持久进入正式 `rw-main`、并随 main 前进做语义审查的个人叠加分支。长期个人功能使用第 1.3 节的 `promote`。一次性不拉取测试使用第 2 节的 `--local-branch`，不要写入持久清单。

前置脚本统一完成：

1. 检查控制面、构建目录、`main` 及清单功能分支 worktree 的洁净度。
2. fetch upstream/origin，将本地 `main` 安全快进到 `upstream/main`，并推送 fork。
3. 批量查询清单 PR，自动删除已经合入且被本地 `main` 包含的项。
4. 按每项的 `reviewed-main` / `reviewed-head` 判断是否需要语义审查。
5. 在输出语义审查 request 前，在临时 detached worktree 中只读模拟 `rw-base + main + overlays` 的实际合并顺序；若冲突，立即报告具体分支和冲突文件并停止，先回源分支修复。该预检不移动正式 refs、不改清单、不安装依赖、不运行构建。
6. 将最新 `main` 合入候选 `rw-base`，再按清单顺序叠加全部临时分支生成完整候选 `rw-main`；不是每层各跑一遍，而是最后只刷新一次跨 workspace 声明并运行一次 format/typecheck/lint。
7. 检查通过后才移动本地 refs，并用一个 atomic push 同时更新 `origin/rw-base` 与 `origin/rw-main`。
8. 成功时原子写 ready state 和 workspace 构建可信 stamp；失败或暂停前删除旧 ready state，防止复用过期结果。

前置脚本在删除旧 state 前取得 `$paseo_build_root/.dev/build-paseo-artifacts.lock`，并持有到整个同步、审查 gate 和重建流程结束。正式产物脚本与 `manage-rw-base.sh` 使用同一把非阻塞锁。ready state 冻结控制面 HEAD、`main`、`rw-base` 与 `rw-main`；正式脚本取得锁后会再次验证全部坐标，任一漂移都停止且不删除旧产物。

readiness stamp 允许同一请求中的安全去重：不同 merge commit 若 Git tree 完全相同，并且 `.tool-versions` / `.mise.toml`、实际 Node/npm 版本、所有依赖与 patch 输入、server/CLI/protocol 等完整 `dist` 摘要都匹配，可复用先前已经通过的 readiness。tree、工具链、依赖输入或任一产物变化都会 cache miss 并完整执行 `npm run build:server`、`format:check`、`typecheck`、`lint`。固定工具链的安装与激活由 `rebuild-rw-main.sh` 统一拥有，prepare 和 lifecycle 每次 rebuild 都只激活一次。正式产物链只接受 exact HEAD 的 stamp；缺失、畸形或损坏时安全回退完整 server build。

### 1.1 退出码与语义审查

- `0`：readiness gate 已通过，可以进入第 2 节。`No-op:` 表示 main、清单和全部分支 head 未变化，可安全复用现有 merge 链。
- `3`：不是脚本故障。脚本会打印 `PASEO_REVIEW_REQUEST_FILE=<绝对路径>`，其内容寻址 TSV 冻结本轮 main 与每条分支的精确审查区间。必须审查 request 中的每一项；阅读全部提交主题、路径，疑似相同能力时继续看 PR 说明和完整 diff。patch 等价或路径重叠只是线索，不是语义结论。
- mergeability 预检失败：属于组合冲突，不进入语义审查。输出会包含失败的 overlay 和冲突文件；回源分支 rebase 最新 `main`、解决冲突并推送后，从头重跑前置流程。
- `4`：清单已原子更新，但尚未重建。运行 `npm run format`，确认仅有预期清单改动，提交 `chore(build): sync rw-main branches` 并推送 `origin/chore/build-paseo`，再不带增删参数重跑。
- 其他非零：立即停止并按日志诊断。没有 ready state 时禁止启动服务端、Android 或 Windows。

语义审查的自动决策：

1. 上游未吸收：保留该分支。
2. 上游已完整吸收：重跑时传 `--remove-branch <分支>`。
3. 上游只吸收一部分：到源功能分支自己的 worktree rebase 最新 `main`、删除重复实现、运行定向验证并 `git push --force-with-lease`，再重新审查。
4. 无法立即确定：AI 继续检查完整 diff、`git range-diff`、路径、测试和上游上下文；仍无法证明完整吸收时默认 `keep`，不得自动删除。整个接受/删除决策由 AI 完成，不等待人工确认。

只有一个简单分支时由主代理直接审查。有至少两个独立待审分支时，主代理按 request 的冻结区间启动最多 3 个只读 reviewer subagent 并行审查；reviewer 不得改 worktree、移动 refs 或运行测试，每条分支单独返回结论和证据。主代理必须核对 request 的分支集合与返回集合完全一致，并且仍是唯一的接受、清单修改、提交和推送决策点。

AI 完成全部项目只能保留或删除的自动决策后，用同一个前置命令追加：

```bash
--accept-review-request "$paseo_review_request_file"
```

其中 `paseo_review_request_file` 取自本轮 `PASEO_REVIEW_REQUEST_FILE`；不要只传 main SHA。若审查期间 main、任一分支 head、待审集合或区间变化，脚本会拒绝旧 request，必须重新审查。若同时删除条目，再追加对应 `--remove-branch`。清单坐标变化同样属于清单改动，按退出码 `4` 的要求提交。提交正文记录审查区间和删改依据。

### 1.2 readiness 失败处理

- 同一 workspace 的 `src`/测试 import 报成员不存在、helper 改名或参数不符，通常是分支组合不兼容。临时叠加层回源功能分支修复；长期功能从维护分支经 `manage-rw-base.sh maintain` 进入。不要直接修改候选、`rw-base` 或 `rw-main`。
- 回源分支做 typecheck/定向测试前先确认该 worktree 的依赖已引导（至少 `node_modules/.bin/tsc`、相关 workspace 依赖可解析）；若只是缺依赖，在源 worktree 执行 `npm install --ignore-scripts` 后重跑，不要把环境缺失当成代码冲突，也不要在审查阶段给所有 worktree 无条件联网安装。
- 只有报错实际跨 workspace 指向生成的 `dist/*.d.ts` 时才先重建声明拥有方：protocol/client 用 `npm run build:client`，server/CLI/relay 链用 `npm run build:server`。
- 源分支修复后运行 `npm run format`、`npm run typecheck`、`npm run lint` 和相关单个测试。app Playwright 定向测试必须显式清空外部密码：`PASEO_PASSWORD= npm run test:e2e --workspace=@getpaseo/app -- <spec>`。
- 完整排查按错误文本查询 [踩坑记录.md](踩坑记录.md)，不要每轮预读全文。

### 1.3 `rw-base` 功能生命周期

状态直接来自 `rw-base` 第一父链上的结构化 trailers，不另建容易漂移的功能清单：

```bash
bash "$paseo_chore_root/dwyanewang/manage-rw-base.sh" \
  --build-root "$paseo_build_root" status
```

`status` 按第一父链提交中的 `Paseo-Base-Feature` / `Paseo-Base-Action` trailers 重建生命周期状态，并把无法归类为 lifecycle 或合法 main sync merge 的提交显式输出为 `UNMANAGED\t<SHA>\t<subject>`。`promote/maintain/retire` 遇到这些提交会拒绝自动推断。用户若说明某项修改已经直接提交并 push，必须先核对真实提交和祖先关系：

```bash
git log --first-parent --decorate --oneline -n 30 rw-base
git show --stat <commit>
git merge-base --is-ancestor <commit> rw-base
```

不能因受管功能列表未显示就推断“尚未迁入”并再次 promote。发现 `UNMANAGED` 时暂停自动生命周期操作，检查当前树是否仍保留其语义并制定显式迁移/清理方案；祖先关系只证明提交进入过历史，不证明后续冲突解决没有丢掉内容。

迁入新功能；首次迁移可重复提供 feature/branch 对：

```bash
bash "$paseo_chore_root/dwyanewang/manage-rw-base.sh" \
  --build-root "$paseo_build_root" --state-file "$paseo_preflight_state" --push promote \
  --feature worktree-checkout-branch --branch feat/worktree-checkout-branch \
  --feature codeup-forge --branch feat/codeup-forge
```

来源分支必须洁净且与 `origin/<branch>` 精确一致。追加修复使用 `maintain --feature ID --branch BRANCH`。每个 promote/maintain 都生成独立 `--no-ff` merge，并记录 feature/action、source branch/head 和 main head trailers；禁止绕开入口直接提交产品变化。

上游提供替代方案后显式退役：

```bash
bash "$paseo_chore_root/dwyanewang/manage-rw-base.sh" \
  --build-root "$paseo_build_root" --state-file "$paseo_preflight_state" --push retire \
  --feature codeup-forge --replacement 'getpaseo/paseo#1234'
```

退役不会盲目 revert。脚本从最新 `main` 开始，按原顺序重放其它 active 功能，验证候选后生成 append-only retirement commit，再原子发布 `rw-base`/`rw-main`。若 main 合并、功能 merge 或重放发生冲突，退出码 `5` 会打印 `PASEO_RW_BASE_OPERATION=<request>` 并保留隔离 worktree；解决并 `git add` 后运行：

```bash
bash "$paseo_chore_root/dwyanewang/manage-rw-base.sh" \
  --build-root "$paseo_build_root" --push continue \
  --operation "$paseo_rw_base_operation"
```

放弃则将 `continue` 换成 `abort`。request 内容寻址并冻结 control/main/base/source 坐标；任一 ref 漂移都拒绝继续。冲突、验证失败或中止前，正式 refs 与 ready state 均保持不变。

构建请求中的 lifecycle 操作必须传与正式产物相同的 `--state-file`。新操作先 fetch upstream/origin、把本地 `main` 快进到最新 `upstream/main` 并同步 `origin/main`，再冻结 main/base/source 坐标；冲突 `continue` 不移动 refs，只先刷新 tracking refs，再按冻结坐标拒绝 upstream、origin 或来源分支漂移。state 路径也冻结进 request，所以 `continue` 不必重复传；`rebuild-rw-main` 在固定 mise 工具链下完成验证、refs 更新和可选 atomic push 后，lifecycle 直接原子生成兼容的 ready state。此时可直接运行第 2 节产物脚本，不再调用 prepare 造成第二轮 readiness。state 写入失败只降级为警告；refs 已成功时随后正常 prepare 可重新生成，不把成功的生命周期操作伪装成失败。

### 1.4 `rw-base` 冲突续跑的双父语义校验

`continue` 前不能只消除冲突标记或复用某个旧候选树。先固定冲突合并的两个父提交，并查看 index 中双方原文：

```bash
paseo_conflict_worktree="$(dirname "$paseo_rw_base_operation")/worktree"
paseo_conflict_ours="$(git -C "$paseo_conflict_worktree" rev-parse HEAD)"
paseo_conflict_theirs="$(git -C "$paseo_conflict_worktree" rev-parse MERGE_HEAD)"
git -C "$paseo_conflict_worktree" ls-files -u
git -C "$paseo_conflict_worktree" show :2:<冲突路径>
git -C "$paseo_conflict_worktree" show :3:<冲突路径>
```

解决并 `git add` 后，必须分别对照两个父提交审查 staged 结果：

```bash
git -C "$paseo_conflict_worktree" diff --cached "$paseo_conflict_ours" -- <冲突路径>
git -C "$paseo_conflict_worktree" diff --cached "$paseo_conflict_theirs" -- <冲突路径>
```

强制规则：

- `add/add` 只表示双方新增了同一路径，不表示任选一侧。双方提供不相交能力时，结果必须取语义并集。
- 冲突文件是 `.patch` 时，逐个检查其中的 `diff --git` 目标；不同目标全部保留，同一目标按 hunk 合并，不能把整个 patch 文件当作普通文本二选一。
- package、patch 路径或 prefix 的 postinstall 注册最终只能保留一份；合并后显式计数，不能因双方都注册而重复执行。
- 以前失败或未经双父验证的候选树只能作为证据，不能作为“已验证模板”复制；树相等不等于语义正确。
- 候选树会静态检查 `scripts/postinstall-patches.mjs`：同一 `(cwd, nodeModulesPath, patchPrefix)` 只能注册一次，同一 patch 文件在一个 cwd 只能应用一次，patch 内部目标必须属于注册的 package；无法可靠解析或映射时直接失败。
- 现有流程本来需要运行 `npm install` 时，脚本会比较旧、新 patch 及注册表，只删除受影响的旧、新 package 根目录，再用这同一次安装从缓存恢复。package 从根目录迁入 workspace 时两处都刷新；patch、注册和依赖一起删除时只清理旧路径，不要求安装恢复已经移除的 package。禁止扩大为删除整个 `node_modules`，也不新增第二次安装。
- `format`、`typecheck`、`lint` 和 server 构建不会验证 Gradle 等补丁语义。安装输出会单独扫描 `patch-package` 错误，并在安装后用反向 dry-run 检查每个已注册 patch 确实存在于依赖树；npm 最终退出码成功不能掩盖 patch 失败。该 gate 同时覆盖正式重建和 `--local-branch` 临时叠加。
- 每个冲突路径都能说明相对两个父提交保留、合并或有依据地删除了什么之后，才允许执行 `continue`。

完整事故诊断见 [踩坑记录.md](踩坑记录.md#同名-patch-的-addadd-必须取语义并集)。

### 1.5 校验次数与上游 Git hook

一次 `rebuild-rw-main.sh` 先完成 `rw-base + main + 全部 overlays`，只对最终候选运行一次完整 readiness。若整次用户请求出现多组 `format:check + typecheck + lint`，说明启动了多次 rebuild/lifecycle，而不是 5 条清单分支加 `rw-base` 各自校验。首先查是否误判未受管提交、重复发起 lifecycle，或在 lifecycle 成功后又多跑了一次 prepare；不要把多轮误编排解释为上游要求每层校验。

上游仓库规则确实要求修改后运行 typecheck/lint，`lefthook.yml` 的 pre-commit typecheck 也没有路径过滤，即使只提交文档仍会运行。控制面准备提交时，先做定向测试、`npm run format` 和一次 lint，再让 pre-commit hook 承担该轮唯一一次全仓 typecheck；不要在提交前手工 typecheck 后紧接着让 hook 重复。若本轮不提交或 hook 没有执行，才显式运行 `npm run typecheck`。

## 2. 正式产物链、临时本地叠加与端选择

readiness 成功后，把 state 原样交给版本化脚本。整个命令作为一个长后台任务运行，等进程输出或结束通知，不现场生成 heredoc，不主动定时轮询：

```bash
bash "$paseo_chore_root/dwyanewang/build-paseo-artifacts.sh" \
  --build-root "$paseo_build_root" \
  --preflight-state "$paseo_preflight_state"
```

用户明确要求“不拉取/不同步”时跳过第 1 节，改用：

```bash
bash "$paseo_chore_root/dwyanewang/build-paseo-artifacts.sh" \
  --build-root "$paseo_build_root" \
  --skip-preflight
```

若还要临时测试一个或多个本地分支，在同一条命令追加可重复的 `--local-branch`：

```bash
bash "$paseo_chore_root/dwyanewang/build-paseo-artifacts.sh" \
  --build-root "$paseo_build_root" \
  --skip-preflight \
  --local-branch fix/electron-explorer-tab-menu \
  --target windows
```

`--local-branch` 仅与 `--skip-preflight` 同用。脚本不 fetch，不读取远端最新状态，也不修改持久清单；它冻结显式分支的本地 SHA，从当前 `rw-main` 建立 `rw-local-build-*` 候选，合并后刷新声明并运行 format/typecheck/lint。源分支若有 worktree 必须洁净。普通退出、构建失败、INT 或 TERM 都由 trap 恢复 `rw-main` 并删除候选。

端选择使用可重复的 `--target`：

| 参数               | 行为                                                         |
| ------------------ | ------------------------------------------------------------ |
| 未传 `--target`    | 保持原有三端：server + Android + Windows                     |
| `--target server`  | 只交付服务端；不准备 app、画像或下载服务                     |
| `--target android` | 构建 app 依赖和 Android 两段；跳过 server/CLI 交付与 Windows |
| `--target windows` | 构建桌面包所需 server/CLI 依赖和 Windows zip；跳过 Android   |
| 重复多个 target    | 构建所选并集；`desktop` 是 `windows` 别名                    |

正常完整同步绝不使用 `--skip-preflight`。其它可选参数：`--download-port <端口>`、`--download-ttl <秒>`、`--no-serve-dist`；默认端口 8800、存活 10800 秒，明确拒绝 6767。

脚本负责且必须保持以下语义：

- 在删除所选旧产物前验证 ready state、`rw-base`/`rw-main` HEAD、两个 worktree 洁净度；跳过同步模式验证当前 checkout。本地叠加模式还冻结每条测试分支 SHA。
- 与 preflight 共享构建目录中的非阻塞独占锁；另一段 preflight 或产物链已运行时立即拒绝，不能让多个代理共享 refs、产物和清理状态。
- 构建前只精确删除本轮所选 APK/当前版本 zip 并把目标写入构建标记；Windows zip 成功校验后，按文件 mtime 保留当前包和最近两个历史 `Paseo-Setup-*-x64.zip`，其余旧 zip 删除。`builder-debug.yml`、`win-unpacked/` 和其它架构/格式不参与轮转。仅 app 目标重生成 terminal-webview，成功或失败均用 EXIT trap 还原。
- server 或 Windows 目标构建并验证 server、CLI、protocol；Android-only 只构建 app 依赖。
- 选中 Android 时，每次 prebuild 后应用 8 个 Metro worker 与 `local-balanced` Hermes；先用单 worker 跑完并验证 Metro/Hermes，再启动 8-worker ARM64 Native 第二段并验证 bundle producer 精确 `UP-TO-DATE`。
- 同时选中 Android 与 Windows 时，Windows 仍受 Android bundle gate 保护；gate 后 `MemAvailable` 至少 16 GiB 则并发，否则串行。Windows-only 不启动 Android，直接运行完整画像链。
- 已选 Android/Windows 使用 cgroup 画像。并发分支失败时终止并等待兄弟进程组，保留隔离日志和真实失败码；只有全部所选目标成功后才进入最终清理与发布。
- 校验新产物、还原 terminal-webview、确认两个 worktree 洁净，再启动下载服务。任何失败保留真实退出码且不生成成功结果文件。

## 3. 结果与校验

每轮目录为 `$paseo_build_root/.dev/build-paseo-runs/<时间>-<PID>/`：

| 文件           | 含义                                                                   |
| -------------- | ---------------------------------------------------------------------- |
| `build.log`    | 完整产物链输出                                                         |
| `stages.log`   | 带时间戳的阶段切换                                                     |
| `*.branch.log` | 已选择的 Android Native / Windows 分支隔离输出                         |
| `exit-status`  | 真实退出码，成功或失败均写                                             |
| `result.env`   | 仅成功时原子生成；包含目标、版本、产物、临时分支 SHA、画像与产物链墙钟 |

所选目标的固定产物：

| 端      | 路径                                                                                    |
| ------- | --------------------------------------------------------------------------------------- |
| 服务端  | `packages/server/dist/server/server/exports.js`，CLI 为 `packages/cli/dist/index.js`    |
| Android | `packages/app/android/app/build/outputs/apk/release/app-release.apk`                    |
| Windows | `packages/desktop/release/Paseo-Setup-<版本>-x64.zip`；目录中同类 zip 最多保留 3 个版本 |

先核对 `paseo_artifact_targets` 和 `paseo_artifact_preflight_mode`。本地叠加模式还要核对 `paseo_artifact_local_overlay_count` 及每条 branch/head。Windows 目标还要核对 `paseo_artifact_windows_retention_limit=3`、`paseo_artifact_windows_archive_count` 和 `paseo_artifact_windows_pruned_count`。已选 Android 的两份和已选 Windows 的一份 summary 必须是 `exit_status=0`，汇报 `command_wall_seconds`、`average_cpu_cores`、`peak_sampled_cpu_cores`、`host_cpu_percent`、`memory_peak_bytes`、`swap_peak_bytes`、`minimum_host_mem_available_bytes`；不要用含采样收尾的 `service_runtime` 代替阶段墙钟。`paseo_artifact_parallel_mode` 还可能是 `android-only`、`windows-only` 或 `not-applicable`。

## 4. 下载服务与交付

产物脚本会为已选 Android/Windows 目标启动下载服务并只暴露本轮目标；server-only 自动不启服务。地址使用脚本打印的实际 LAN/Tailscale 值，不要写死 VM IP。Tailscale 未登录只会少一个地址，不是构建失败。需要刷新或提前停止时从控制面运行：

```bash
bash "$paseo_chore_root/dwyanewang/serve-dist.sh" keep
bash "$paseo_chore_root/dwyanewang/serve-dist.sh" stop
```

`keep` 从本轮构建标记恢复目标，只刷新所选产物且不重置原 TTL；也可显式传 `--target android|windows`，但必须与标记一致。`stop` 只停止状态文件中身份匹配的自有服务。未知端口占用时报告，不杀其他进程。

最终汇报：持久清单增删及提交（若有）、临时本地分支及冻结 SHA（若有）、所选产物路径/体积/mtime、Windows 历史 zip 保留/清理数量、已选端资源数据、适用时的并发/回退模式、下载地址和真实总墙钟。总墙钟从用户发起打包开始，到产物复核与下载服务就绪结束；`paseo_artifact_total_seconds` 只代表正式产物链，不能扣除阅读、审查、冲突修复或失败重试。
