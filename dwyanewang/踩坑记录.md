## Android：内存、缓存和 Hermes

### 内存与两段构建

旧的一次性 release 构建会让 Hermes（实测 RSS 约 9.7 GB）与 NDK/CMake 并发，在 17 GB 机器上曾于 40 分钟后 exit 137。`-Dorg.gradle.jvmargs=-Xmx...` 只限制 Gradle JVM，不能限制 Hermes 子进程；给 Hermes 强加 6 GB cgroup 上限只会更早 OOM。

当前构建机为 27 GB / 20 核，标准策略是：

- 第一段只跑 `:app:createBundleReleaseJsAndAssets`，Gradle 单 worker；Metro 自己使用 8 worker。
- bundle 非空后，第二段用 8 个 Gradle worker 构建 ARM64 原生库与 APK。
- 第二段先单独运行，只有实时确认 bundle producer 为 `UP-TO-DATE` 后才允许启动 Windows；此时 `MemAvailable` 至少 16 GiB 才并发，否则保持串行。不要清理 Gradle、Metro、`.cxx` 或各模块 `build/` 缓存。
- 若画像显示持续 swap、OOM，或内存峰值接近 22～24 GB，先把原生段降到 6 worker；不要重新把 Hermes 与 NDK 合成一段。
- 个人 APK 固定 `arm64-v8a`，release 使用 debug keystore，只适合自测，不能上架。

这些参数已固化在 `build-paseo-artifacts.sh`。改参数时同步更新定向测试，并用下一次完整构建的同口径画像判断，不用热缓存单次墙钟下结论。

### Metro cache 与 `local-balanced`

Gradle 原生任务几乎全命中缓存时，Android 仍可能慢在 `createBundleReleaseJsAndAssets`。React Native 0.81 的 bundle task 会传 `--reset-cache`；旧生成工程还曾把 Metro 限为 2/4 worker，导致 5074 个模块 transform 约 402 秒。

`configure-android-build.sh` 必须在每次 Expo prebuild 后执行。它：

- 追加 Expo 支持的 `--reset-cache false`，保留按文件内容与 transformer 配置寻址的 Metro transform cache；源码变化时仍生成新最终 bundle，不复用旧 APK。
- 将 Metro worker 调为 8；第一段 Gradle 的单 worker不会把 Metro 降成单 worker。
- 将本地 Hermes profile 设为 `local-balanced`：保留 `-O` 运行时优化，只跳过 Hermes Source Map 生成与合并。

`local-balanced` 不降低应用运行性能，但该本地 APK 的 JS 崩溃堆栈不能通过 Hermes Source Map 还原；Java/Kotlin 堆栈和 R8/ProGuard mapping 不受影响。需要排查 Release JS 崩溃时临时用 `--hermes-profile production`。EAS/正式云构建不调用此脚本，仍保留 Source Map。

即使 Metro transform 从约 402 秒降到约 51 秒，Hermes 仍需全量字节码编译，整段曾仍为约 12 分钟。Hermes 长时间只用约 1～2 核时，继续增加 Gradle/Metro worker不会加速这部分；这通常是当前工具链的串行瓶颈，不是缓存失效。

### bundle producer 必须保留

第二段不能传 `-x :app:createBundleReleaseJsAndAssets`。React Native Gradle 插件把该任务输出注册为 generated resources/assets；Gradle 8.14.3 排除 producer 会在 `:app:mapReleaseSourceSetPaths` 报 provider 尚未完成。

正确做法是第一段成功且 bundle 非空后，在同一生成工程与环境运行第二段，让 producer 留在 task graph 并出现：

```text
> Task :app:createBundleReleaseJsAndAssets UP-TO-DATE
```

若第二段重新执行 bundle，停止并检查第一段结果、环境/参数是否一致，不要继续用来源不明的 bundle 封包。

Windows `expo export` 会写 `packages/app/dist`，而 React Native bundle task 会扫描 app 的 JS/TS 输入；因此不能先启动 Windows、再在两支结束后检查 producer。后置 grep 只能追责，无法阻止 Hermes 与 Windows 叠峰。正式脚本必须先单独启动 Native，实时看到上述精确行后，再做内存判定并启动 Windows。

### cgroup 资源画像与 systemd 收尾

单个 PID、`top` 截图或 `/usr/bin/time -v` 无法覆盖 Gradle、Node、Metro、Hermes、CMake、Wine 与 electron-builder 的全部后代。Android 两段和 Windows 整链均通过 `profile-build-resources.sh` 进入 transient cgroup，产生：

- `<label>.samples.tsv`：每秒的整组 CPU、内存、swap、进程数与主机可用内存。
- `<label>.summary`：真实命令墙钟、平均/采样峰值核心数、20 核整机占比、精确内存/swap 峰值。
- `<label>.transcript.log` 与内部 command-result。

曾因 systemd inotify/cgroup watch 耗尽，Gradle 已 `BUILD SUCCESSFUL` 后 service 又等 90 秒并返回 timeout，summary 平均值变成 `unknown`。当前 wrapper 以 cgroup 内原子 command-result 为命令退出码和聚合数据权威，`TimeoutStopSec=3s`，并用 `systemd-run --collect` 在成功或失败后卸载 transient unit，避免失败 unit 元数据继续累积；systemd 清理异常只记 `systemd_cleanup_degraded=1`，不能覆盖成功命令。command-result 缺失或不完整仍应判失败。

并发分支失败时不能一开始就向 profile 的整个进程组广播 TERM：这会同时杀掉 `systemd-run`/`tee`，使 wrapper 来不及通过 EXIT trap 停止独立的 transient unit，Gradle/Wine 后代会继续留在 cgroup 中。协调器先只 TERM profile leader，给 wrapper 完成 `systemctl stop` 的窗口；超时后才对剩余进程组 TERM/KILL。真实 cgroup 外部终止测试必须验证 unit 内后代消失，不能只验证 fake leader 退出。

比较阶段耗时使用 `command_wall_seconds`，不用包含采样收尾宽限的 `service_runtime`。平均不到 2 核可能只是热缓存下没有并行任务；不能据此盲目增加 worker。

## Windows：Wine 与打包告警

Linux 上 electron-builder 需要 Wine 执行 32 位 `rcedit-ia32.exe`。仅在对应错误出现时修复：

```bash
sudo dpkg --add-architecture i386
sudo apt-get update
sudo apt-get install -y wine32:i386
sudo dpkg --configure -a
sudo apt-get install -f -y
```

`dpkg -l` 中 `wine32:i386` 应为 `ii`，不是 `iU`。若仍报 `syswow64\\ntdll.dll error c0000135`，说明专用 prefix 在安装 wine32 前创建且缺 32 位子系统。备份后重建专用 prefix；绝不删除默认 `~/.wine`：

```bash
paseo_wineprefix="$HOME/.local/share/paseo/wineprefix"
if [[ -e "$paseo_wineprefix" ]]; then
  mv -- "$paseo_wineprefix" "${paseo_wineprefix}.backup-$(date +%Y%m%d-%H%M%S)"
fi
WINEPREFIX="$paseo_wineprefix" WINEARCH=win64 wineboot --init
test -f "$paseo_wineprefix/drive_c/windows/syswow64/ntdll.dll"
```

electron-builder 可能打印 `@codemirror/autocomplete` missing，但如果 expo export 和 electron-builder 都 exit 0、zip 正常且 web bundle 包含 C# grammar，这是 `@replit/codemirror-lang-csharp` 的未满足 peer 诊断，不影响当前语法高亮路径。不要为消除告警擅自安装依赖或改 lockfile。

若安装后的桌面端实际报 `ERR_MODULE_NOT_FOUND`，且导入方位于 `app.asar/node_modules`，则不是上述良性构建告警。electron-builder 不保证收集只由 npm peer 自动补齐的运行时包；应在真正使用该模块的 workspace `dependencies` 中显式声明缺失包、更新 lockfile，并在重打包后用 `asar list` 确认依赖已进入 `app.asar`。只在构建机临时执行 `npm install` 会掩盖问题，不能修复已发布的 zip。

兜底时删除 `electron-builder.yml` 的 `win.icon` 可绕过 rcedit，但会失去正确图标和版本元数据；默认应修好 Wine。

## 类型错误与定向测试

npm workspace 包会从被 Git 忽略的 `dist/*.d.ts` 互相解析，切分支不会自动刷新它们。判断顺序：

1. 报错是否真实跨 workspace 指向另一包的 `dist/*.d.ts`？是则重建声明拥有方：protocol/client 用 `npm run build:client`，server/CLI/relay 链用 `npm run build:server`。
2. 源功能 worktree 是否有完整依赖（例如 `node_modules/.bin/tsc`、`fake-indexeddb`、`expo-sqlite`）？缺失时先在该 worktree 执行 `npm install --ignore-scripts`，再判断代码错误；不要为每个审查 worktree 无条件自动安装。
3. 双方都在同一 workspace 的 `src`、`e2e` 或 helper 下？这是分支源码组合不兼容。按 Git 归属在源功能分支 rebase/main 后修复，不能加重复类型来掩盖。

`rebuild-rw-main.sh` 已在 typecheck 前通过 `npm run build:server` 刷新 protocol/client/highlight/plugin/relay/server/CLI 声明。从非 `rw-main` 切入构建目录时还会运行 `npm install`；不要手工切分支后拿旧 `dist` 诊断。只刷新 client 链仍可能让 CLI 读到旧 server `dist`，例如协议新增 timeline item 后出现两个 `AgentTimelineItem` 不兼容的假象。

app Playwright 隔离 daemon 会展开父进程环境；`.env.test` 没写 `PASEO_PASSWORD` 不代表父变量被删除。若日志显示 `authRequired=true`，定向测试显式清空：

```bash
PASEO_PASSWORD= npm run test:e2e --workspace=@getpaseo/app -- <spec>
```

这不会修改或重启 6767 主 daemon。不要把认证超时先误判为端口或 server `dist` 问题。

## 语义审查与构建拓扑

`chore/build-paseo` 是控制面，`main` 是纯上游镜像，`rw-base` 是长期本地功能基线，`rw-main` 是最终产品树。控制脚本必须从 chore worktree 调用并显式传 `/home/yangfei/Projects/paseo`。

上游可能通过另一个 PR、直接提交或不同架构吸收临时叠加功能，而原 PR 仍 OPEN/CLOSED。Git 冲突、typecheck、patch 等价和路径重叠都不能证明语义是否重复。因此叠加清单每项分别记录 `reviewed-main` 和 `reviewed-head`：main 或分支 head 变化都以退出码 3 强制重新审查。明确转为长期本地能力的功能迁入 `rw-base` 后不再参与逐轮审查。

前置同步现在会在输出语义审查 request 前，用临时 detached worktree 只读模拟 `rw-base + main + overlays` 的真实合并顺序。它只提前发现 Git 组合冲突并报告 overlay/文件，不移动正式 refs、不改清单、不安装依赖；冲突仍需回源分支 rebase/修复，不能把这个预检当作语义结论。

处理原则：未吸收保留，完整吸收删除，部分吸收回源分支 rebase/删重/验证。rebase 后先看 `git range-diff`，能证明 feature commits 保持等价且只有冲突解决调整时做增量审查，否则做完整审查。AI 自行完成接受/删除决策；无法证明完整吸收时默认 `keep`，不自动删除，也不向用户请求人工确认。退出码 3 会生成内容寻址的冻结 review request；多个独立分支可交给最多 3 个只读 reviewer subagent 按精确 SHA 区间并行审查，但主代理仍是唯一接受与修改者。接受时必须用 `--accept-review-request` 同时验证当前 main、全部待审分支 head、集合和区间；任一 ref 漂移都重新审查。首次建立坐标时不能直接标成当前 main 来跳过历史审查。

同步 `main` 前必须查是否已被另一个 worktree 签出：已签出就在那个洁净 worktree `merge --ff-only upstream/main`，未签出才安全移动共享 ref。日常构建只把 main 合入 `rw-base`，不 rebase 长期功能；重建失败保持原 `rw-base`/`rw-main` 不变。

`rw-base` 不能自动理解上游重构是否语义替代了本地功能。正常 main 合并无冲突时会继续保留本地能力；确认替代后必须显式 `retire`。退役从最新 main 重放其余 active 功能，而不是直接反转旧 merge diff，否则可能误删上游后来修改的同一代码。所有本地基线变化必须带生命周期 trailers，直接提交会让安全重放失去边界。

### `manage-rw-base status` 不等于完整 `rw-base` 历史

2026-09-03 的 Android NDK 事故中，提交 `a43b1abeb42dcd2a8b143ede55a55bba69520026`（`fix(android): align Unistyles NDK version`）已经直接进入并 push 到 `rw-base`，但没有 `Paseo-Base-Feature` / `Paseo-Base-Action` trailers。后来 `ef34e091d7dab4fb8acfb5d39da574626d7489ad` 在最新 main 上重新提交相同 NDK hunk，并由 `69130b32b6bde5cedca6ffae1fbb511bd545c4e8` 作为 `unistyles-ndk-version` 正式 promote；因此功能语义已经纳管，旧直提提交只是尚未记录迁移关系。受管功能状态仍不等于分支包含的全部提交或代码。

用户说明某项修改已经提交时，诊断顺序必须是：

```bash
git log --first-parent --decorate --oneline -n 30 rw-base
git show --stat <commit>
git merge-base --is-ancestor <commit> rw-base
```

然后检查当前树中的实际语义。`a43b1abeb` 确实是后来 main 合并提交 `3bd829e83ef5f132fdb8278cfa04ed1275db2edb` 的第一父，说明拓扑上的合并顺序正确；但提交是祖先只证明它进入过历史，不能证明后续冲突解决仍保留其内容。不能仅因 `status` 缺项就再次 promote；遇到这种未受管直提提交，应停止自动生命周期推断，先审查祖先关系、当前树和冲突结果。确认后续 active 功能完整接管时，在下一次相关 `maintain` 中显式传 `--adopt-commit <SHA>`，由 `Paseo-Base-Adopted-Commit` trailer 追加记录迁移关系；不要删除或改写已推送的提交历史，也不要按相同标题自动判断。

### 同名 `.patch` 的 `add/add` 必须取语义并集

同一次事故中，`rw-base` 与上游 main 都新增了 `patches/react-native-unistyles+3.2.4.patch`：本地版本包含 Android `build.gradle` 的 NDK 修复，上游版本包含 Web registry 清理。两项能力并不互斥，正确结果应同时保留 Web hunks、Android NDK hunk，并让 `scripts/postinstall-patches.mjs` 中对应注册只出现一次。

第一次冲突解决生成的 `e6831a002544c87112ce941f833cc9af31d4ac50` 选择了上游 patch 文件，丢失 NDK hunk，同时重复了 postinstall 注册。第二轮又把这个候选当作“已验证树”复制，因此完整复现了错误。与旧候选树相等只能证明复现，不能证明语义正确；typecheck、lint 和 server build 也不会检查 Gradle patch 的效果。

此类冲突按以下清单处理：

1. 用 `git show :2:<路径>` 和 `git show :3:<路径>` 阅读双方原文，不能把 `add/add` 当作二选一。
2. 对 `.patch` 枚举内部每个 `diff --git` 目标；目标不同则取并集，目标相同则逐 hunk 解决。
3. staged 结果分别 diff 两个父提交，逐项说明保留、合并或删除的依据。
4. 检查 package、patch 路径和 prefix 注册次数，最终必须为一份。
5. 在干净依赖副本或精确刷新过的目标包上应用 patch，并直接检查被修改的目标文件。

特别注意持久 `node_modules` 陷阱：如果依赖文件已经应用过旧的 Web patch，再应用扩展后的组合 patch 会因上下文已变化而失败；`patch-package` 虽然打印错误，npm 脚本仍可能继续，最终退出码不能单独作为成功证据。

现在 `rebuild-rw-main.sh` 和 `--local-branch` 的依赖变化路径会在原有单次 `npm install` 前静态校验注册唯一性与 patch 目标，并精确移除新候选注册表中的全部 patch-managed package。不能只删除本轮发生变化的 Unistyles 等 package：postinstall 会重放全部注册 patch，未变化但已经打过 patch 的 `@mattermost/paste-input`、`react-native-draggable-flatlist` 等持久 package 若不先恢复为干净安装，就会发生二次应用。注册从根 `node_modules` 迁移到 workspace 时还会清理旧路径；patch、注册和依赖一起删除时只清旧路径，不把已删除 package 列为安装后必需项。安装后既扫描 patch-package 错误文本，也反向验证候选依赖树中的真实应用结果。验证先使用 `git apply --reverse --check`；Mattermost patch 内部的零上下文 hunk 可能已经由 patch-package 正确应用却被 Git 默认拒绝，因此 Git 失败时再用 `patch --dry-run --reverse --batch -p1` 兜底。新文件型 patch 可能相反地只通过 Git，所以不能只选一种工具；仅当两者均失败时才判定未应用，并保留两份错误。任何无法可靠映射的变化都停止，不扩大为清空整个 `node_modules`，也不增加第二次安装。详细强制规则和续跑 gate 见 [打包流程.md](打包流程.md#14-rw-base-冲突续跑的双父语义校验)。

## 编排性能与总耗时

### 多轮 lifecycle 会重复触发完整 readiness

单次 `rebuild-rw-main.sh` 并不会给 `rw-base` 和清单中的每条分支各跑一次校验；它先顺序合并所有层，最后只对完整 `rw-main` 候选执行一组 `build:server + format:check + typecheck + lint`。2026-09-03 的构建之所以看见多组，是因为代理重复启动了多轮 lifecycle，而每轮都调用一次 rebuild。

当时 `e6831a002`（12:47）、`3bd829e83`（13:14）和 `7b4b3372c`（13:16）是三个不同 commit，但 tree 都是 `a0e3eacc08358f12a20d074cd4463822ec2b94c8`。后两次对同一错误 tree 再跑完整 checks 没有增加证据，只增加耗时。现在的强制策略是：

1. 未受管 `rw-base` 提交 gate 和冻结冲突 request 防止误判后另起一轮 lifecycle；冲突必须 `continue` 原操作。
2. lifecycle 成功后直接写正式产物可消费的 ready state，不再随后重复 prepare。
3. 同一 Git tree 只有在固定工具链、实际 Node/npm、依赖/patch 输入及完整 dist 摘要都一致时才复用 readiness；任一项变化都完整重跑。
4. `.patch` 双父语义和安装验证在 stamp 判断前执行，因此缓存不能绕过 patch target 并集、唯一注册或真实应用检查。

上游的校验要求是另一件事：仓库规则要求修改后 typecheck/lint，`lefthook.yml` 还会对每次提交无条件运行全仓 typecheck，所以只改文档也会触发它。控制面即将提交时不手工预跑第二遍全仓 typecheck；定向测试、format、lint 完成后由 pre-commit hook 承担唯一一次，只有不提交或 hook 未执行时才显式 typecheck。

曾经 no-op 前置的真实机器命令仅约 24 秒，代理分轮预检、fetch、逐个 GitHub 请求和重复阅读却花约 5 分钟。后来批量 GraphQL 与 `prepare-rw-main-for-build.sh` 将一次 no-op 前置降到约 11 秒；语义审查、冲突修复、typecheck/lint 仍是必要 gate，不能为追求速度跳过。

前置完成后，代理现场重新推理并拼 heredoc 又曾空耗约 2 分钟。现在正式三端链固定由 `build-paseo-artifacts.sh` 单次执行，统一管理阶段日志、真实退出码、清理、画像、产物和下载服务。版本化编排减少的是控制面等待和流程漂移，不会让 Metro、Hermes、Gradle 或 electron-builder 本身变快。

多个代理不能各自在 `/home/yangfei/Projects/paseo` 启动一端构建：它们会竞争 terminal-webview、固定产物、构建标记、Metro/Electron 缓存、Wine prefix 和最终清理。正式链只保留一个 owner；preflight 与产物脚本共用整轮独占锁。Hermes 完成后先单独启动 Android Native，producer gate 通过且 `MemAvailable` 至少 16 GiB 才并发 Windows，失败时回收兄弟进程组；否则自动串行回退。subagent 只用于多分支只读语义审查，不取代确定性的构建编排。

脚本的 `paseo_artifact_total_seconds` 只包含正式产物链。对用户的总耗时必须从打包消息开始，到下载服务就绪结束，包括读流程、同步、语义审查、冲突处理、失败重试和最终校验；热缓存阶段或只累加成功阶段不能替代真实墙钟。

## 其它环境笔记

- 新 shell 中 mise 可能未激活；始终以仓库 pin 为准，不硬编码 mise 安装目录。版本化脚本会自行激活。
- SSH push 偶发 `Connection closed ... port 22` 通常是网络抖动，可重试；不要因此改 remote 或凭据。
- Tailscale 是可选下载通道，不是构建 gate。未授权或控制面网络异常时保留 LAN 地址；首次网页登录单独完成，不让它推翻已成功构建。
- VM 出站可能不能访问物理机，因此由物理机浏览器主动打开 `serve-dist.sh` 实际打印的地址；不要写死 IP，也不要从 VM 强推文件。
- APK/zip 超过常见聊天附件上限，使用下载服务、U 盘或 `adb install -r` 分发。
