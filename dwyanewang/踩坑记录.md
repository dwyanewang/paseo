# Paseo 三端本地打包踩坑记录

> 环境：Ubuntu 24.04 (Noble) · 27 GB 内存 / 20 核 · Node 22 (mise) · Java 21 (mise) · Android SDK (mise)
> 版本：以根目录 `package.json` 为准
> 目标：本地拉取最新代码 → 打包服务端 → 安卓 APK → Windows x64 桌面端

---

## 坑 1：npm install 残留临时目录导致 `.bin` 软链缺失

**现象**

- 第一次 `npm install` 报 `ENOTEMPTY`，随后 `npm run build` 报 `tsc: not found`。
- `node_modules/.bin/` 里几乎是空的（只剩 1 个条目）。

**根因**

- `node_modules` 里有遗留的 `.vitest-xxxx` 临时目录，导致 install 中途中止，typescript 等包的 bin 软链没被创建。

**解法**

```bash
rm -rf node_modules/**/.vitest-*
npm rebuild        # 重建所有 .bin 软链（含 tsc）
```

之后 `npm run build:server` 正常。

**教训**

- 排查构建时不要用 `| tail` 截断输出，会盖掉真正的报错。应把完整输出重定向到文件再 grep。

## 坑 2：误判“服务端没构建成功”（入口不是 index.js）

**现象**

- `build:server` 退出码 0，但去找 `packages/server/dist/index.js`、`packages/protocol/dist/index.js` 时显示 MISSING，一度以为构建失败。

**根因**

- server / protocol 用的是 `package.json` 的 `exports` 字段，不是 `main: index.js`：
  - server 入口：`dist/server/server/exports.js`
  - protocol：逐文件导出 `dist/*.js`
- dist 其实都已生成，只是找错了文件名。

**解法 / 教训**

- 判断一个包是否构建成功，先看它 `package.json` 的 `main` / `exports` 指向哪里，再去核对那个真实入口文件，别想当然找 `index.js`。

## 坑 3：Android 构建爆内存 / 进程被杀

**现象**

- `npm run android:release` 默认 gradle 配置开了过多 worker，CPU/内存被打满，机器被迫重启，gradle 进程被杀。
- 重启后 `/tmp` 被清空，需要重来。

**根因**

- Gradle 默认并发太高；NDK 原生编译（reanimated / worklets 的 C++）尤其吃资源。
- Release 构建还会在同一次 Gradle 调用里运行 Metro/Hermes。2026-08-01 构建机仍为 17 GB 内存时，实测原配置（4 worker、4 GB Gradle heap、parallel）在 40m24s 后因 Hermes exit 137 失败；Hermes RSS 约 9.7 GB，与原生并发叠加后超出当时的整机内存。
- `-Dorg.gradle.jvmargs="-Xmx..."` 限制的是 Gradle JVM，不是 Hermes 子进程。Hermes 没有可支持的 6 GB heap 上限参数，强行用 cgroup 压到 6 GB 只会更早触发 exit 137。

**解法**

- 把 Hermes 和 NDK/封包拆成两次 Gradle 调用。第一段任务本身无可并行的 CMake 任务，单 worker 可避免内存峰值；2026-08-07 构建机扩容到 27 GB / 20 核后，第二段让 bundle 命中 `UP-TO-DATE` 并使用 8 worker 加速原生编译。代价是多一次 Gradle 配置，换来更低的失败概率；若观察到持续 swap 或 OOM，第二段先降为 6 worker。
- 个人自用 APK 只编译 `arm64-v8a`，不再重复编译 32 位 ARM 和 x86 ABI：

```bash
./gradlew :app:createBundleReleaseJsAndAssets \
  --no-daemon --no-parallel --max-workers=1 \
  -Dorg.gradle.jvmargs="-Xmx2g -XX:MaxMetaspaceSize=768m" \
  -PreactNativeArchitectures=arm64-v8a

test -s app/build/generated/assets/createBundleReleaseJsAndAssets/index.android.bundle
./gradlew assembleRelease -x :app:createBundleReleaseJsAndAssets \
  --no-daemon --parallel --max-workers=8 \
  -Dorg.gradle.jvmargs="-Xmx4g -XX:MaxMetaspaceSize=1024m" \
  -PreactNativeArchitectures=arm64-v8a
```

- SDK、Gradle 缓存、原生编译产物（`.cxx`、各模块 `build/`）**不要清理**，留着给下次复用。ARM64-only 新配置的耗时以下一次完整构建实测为准，不沿用旧四 ABI 的 ~17/~5 分钟估算。

**附：Android SDK 不完整问题**

- 初始只有 `cmdline-tools`，缺 platform-tools/build-tools/platforms/ndk，报 `spawn adb ENOENT` / `Failed to resolve Android SDK path`。
- 解法：用 `sdkmanager` 补装 platform-tools、platforms;android-35、build-tools;35.0.0、ndk;27.1.12297006、cmake;3.22.1，并写 `android/local.properties`：
  ```
  sdk.dir=/home/yangfei/.local/share/mise/installs/android-sdk/21.0
  ```
- mise 没在 shell 激活时，构建命令要显式带环境变量（见流程文档）。
- release 包用 **debug keystore** 签名（build.gradle 里 `release.signingConfig = signingConfigs.debug`），自测够用，**不能上架商店**。

**附：expo prebuild 的 `--non-interactive` 在 expo CLI 54+ 被删（2026-06 这次踩到）**

- **现象**：`expo prebuild --platform android --non-interactive` 先打印 `--non-interactive is not supported, use $CI=1 instead`，紧接着报 `Invalid project root: .../packages/app/ ` 并以 exit 1 失败。该 flag 被当成未知位置参数，污染了 project root 解析。
- **更阴险的点**：当时把命令写成 `prebuild ... && gradlew ...`，结尾又加了 `echo "EXIT=$?"`——echo 永远成功，导致整段后台任务"退出码 0"，**假成功**。而 `app-release.apk` 是上一次构建的旧产物（按 mtime 一眼能看出是昨天的），差点误判打包成功。
- **解法**：去掉 `--non-interactive`，只靠已设的 `CI=1` 走非交互。
- **教训**：① 校验产物别只看 exit code，要看 `ls -lh` 的**修改时间**是否是本次；② 用 `&&` 串命令时，别在结尾用 `echo` 兜底退出码，会把失败洗成成功——要 `tee` 真实 `$?` 或直接看子命令退出码。

**附：BUILD SUCCESSFUL 但 APK mtime 还是旧的——增量构建 UP-TO-DATE，是真成功不是失败（2026-06-10 踩到）**

- **现象**：`./gradlew assembleRelease` 退出码 0、日志有 `BUILD SUCCESSFUL`，但 `app-release.apk` 的 mtime 是上次构建（昨天）的，不是本次。乍看像坑 3 的"假成功"。
- **根因**：gradle 增量构建。本次 `:app:createBundleReleaseJsAndAssets`（Metro 重打 JS bundle）虽 executed，但产物与上次**字节一致**，下游 `:app:packageRelease`/`:app:assembleRelease` 遂判为 `UP-TO-DATE`、不重封包，APK 保留旧 mtime。bundle 为何字节一致：第 1.5 节重生成的 `terminal-emulator-webview-html.ts` 只是 TS 外层 oxfmt 格式变了，导出的 HTML **字符串字面量内容不变**，Metro 取字符串值 → bundle 不变；且本次合并只动了 `packages/desktop`（不进 APK）。
- **判断真假**：与坑 3 的"echo 洗成功"相反，这是**真成功**，旧 APK 内容即当前内容。决定性证据看 task 状态：`grep "actionable task"`（X executed / Y up-to-date）、`grep ":app:packageRelease"` 是否 `UP-TO-DATE`。`packageRelease` UP-TO-DATE = 输入未变 = 现有 APK 已是最新。
- **要新 mtime（分发产物图省心、可验证）**：`rm -f .../app/build/outputs/apk/release/app-release.apk` 后带上同样的 `-PreactNativeArchitectures=arm64-v8a` 重跑 `assembleRelease`——只重跑封包（bundle 缓存命中，~2min），出字节相同但时间戳新鲜的 APK。

## 坑 4（Windows 重点）：在 Linux 上用 electron-builder 打 Windows 包，wine 三连坑

electron-builder 在 Linux 上打 Windows 包，需要 wine 运行 `rcedit-ia32.exe`（给 exe 写图标 / 版本号等资源）。这里连续踩了三个坑：

### 4.1 缺 wine32

- **现象**：`wine --version` 提示 `it looks like wine32 is missing`，electron-builder 在 rcedit 步骤 `FAIL_ELECTRON_BUILDER=1`。
- **根因**：rcedit-ia32.exe 是 32 位程序，必须有 32 位 wine。
- **解法**（Ubuntu 24.04 包名就是 `wine32:i386`）：

```bash
sudo dpkg --add-architecture i386
sudo apt-get update
sudo apt-get install -y wine32:i386
```

> 注：`mise` / `chrome` 等第三方 apt 源不支持 i386，会打印 `N: ... 跳过 ...` 提示，那是**提示不是错误**，主源有 i386 包，忽略即可。

### 4.2 包状态卡在 `iU`（unpacked but not configured）

- **现象**：装了之后 `dpkg -l | grep wine32` 显示 `iU` 而不是 `ii`，wine 仍提示缺 wine32。
- **根因**：apt 安装中途没配置完成。
- **解法**：

```bash
sudo dpkg --configure -a
sudo apt-get install -f -y   # 如有依赖缺失
```

确认变成 `ii` 为止。

### 4.3 装完仍报 `syswow64\ntdll.dll error c0000135`

- **现象**：wine32 已是 `ii`，但 electron-builder 仍失败：
  ```
  wine: failed to load L"\\??\\C:\\windows\\syswow64\\ntdll.dll" error c0000135
  ```
- **根因**：旧 prefix 是在装 wine32 **之前**创建的，里面没有 32 位子系统（syswow64 为空）。装了 wine32 包并不会自动补全已存在的 prefix。
- **解法**：为 Paseo 使用独立 prefix；已有专用目录先备份再初始化，绝不删除默认 `~/.wine`：

```bash
paseo_wineprefix="$HOME/.local/share/paseo/wineprefix"
mkdir -p "$(dirname "$paseo_wineprefix")"
if [[ -e "$paseo_wineprefix" ]]; then
  mv -- "$paseo_wineprefix" "${paseo_wineprefix}.backup-$(date +%Y%m%d-%H%M%S)"
fi
export WINEPREFIX="$paseo_wineprefix"
WINEARCH=win64 wineboot --init
# 验证 32 位子系统已生成：
ls -la "$WINEPREFIX/drive_c/windows/syswow64/ntdll.dll" # 应存在（~3M）
# 验证 rcedit 能跑：
wine ~/.cache/electron-builder/winCodeSign/winCodeSign-2.6.0/rcedit-ia32.exe --help
```

之后续打即成功。

> **兜底方案**（不想折腾 wine）：去掉 `electron-builder.yml` 里 `win.icon` 配置，electron-builder 就不调 rcedit、不需要 wine，直接出 exe/zip。代价：exe 用 Electron 默认图标、缺文件版本号元数据。本次最终走的是修好 wine 的原生方案，产物带正确图标和版本号。

## 坑 5：Windows expo export 用裸 `cross-env` → exit 127 command not found

**现象**

- 流程文档 4.1/速查里 Windows 那步 `( cd packages/app && cross-env PASEO_WEB_PLATFORM=electron npx expo export --platform web )`，在非交互/后台 shell 里跑直接 `cross-env: 未找到命令`，整条链路 exit 127——`build:app-deps` 已成功，卡在它的下一步。

**根因**

- `cross-env` 是 workspace 本地依赖，hoist 在仓库根 `node_modules/.bin`，**没进系统 PATH**；`packages/app/node_modules/.bin/cross-env` 甚至不存在。只有 npm script 上下文或 `npx cross-env` 才解析得到。
- 安卓步骤 `CI=1 npx cross-env APP_VARIANT=production expo prebuild` 没踩到，是因为它走的是 **`npx` cross-env**；Windows 这条是**裸 `cross-env`**，PATH 里没有。
- 之前在激活 mise 的交互 shell 里打包能成，是那种 shell 把 `node_modules/.bin` 注进了 PATH；自动化/后台 shell 没有，于是暴露。

**解法**

- 设环境变量 bash 原生就行，不必依赖 cross-env。去掉它：

```bash
( cd packages/app && PASEO_WEB_PLATFORM=electron npx expo export --platform web )
```

- 流程文档已同步改成这个写法。要保留 cross-env 则必须写成 `npx cross-env`。

**教训**

- 自动化/后台 shell 里别假设 `node_modules/.bin` 在 PATH；本地 bin 一律走 `npx <bin>` 或 npm script，或用 bash 原生 `VAR=value cmd` 设环境变量。
- exit 127 = command not found，第一反应查 PATH / 是不是本地 bin。

## 坑 6：electron-builder 报 `@codemirror/autocomplete` missing —— 良性，别去装（2026-07-01 打 0.1.102 踩到）

**现象**

- Windows 打包链末尾 electron-builder 的依赖收集器打印，整条构建仍 exit 0、zip 正常产出：
  ```
  npm error missing: @codemirror/autocomplete@^6.0.0, required by @replit/codemirror-lang-csharp@6.2.0
  ```

**根因**

- `packages/highlight` 依赖 `@replit/codemirror-lang-csharp`（上游 #1651 加的 C# 语法高亮）。该包把 `@codemirror/autocomplete` 声明为（未满足的 peer）依赖，但 lockfile 里没有它、`npm install` 后 node_modules 也没装（`grep -c "node_modules/@codemirror/autocomplete" package-lock.json` = 0）。
- electron-builder 扫 **node 侧**依赖树做 `npm ls` 时报这条 unmet；beta.1 / beta.2 同版本一样有。

**为什么是良性（判定依据，三条都验过）**

- highlight 只用 C# 的**语法 grammar**、不碰它的 autocomplete 集成，那条代码路径 Metro 根本没触达 → expo export **零解析错误、exit 0**（`grep -iE "unable to resolve|@codemirror/autocomplete" 构建日志` 无命中）。
- C# 语法**确实打进了 web bundle**（`packages/app/dist/_expo/static/js/web/index-*.js` 里能 grep 到 `csharp`）。
- 桌面端装的是 expo 导出的 web bundle（自包含产物），electron-builder 的 node 侧告警不影响它。

**结论**

- 不要为消除告警去 `npm install @codemirror/autocomplete`——会污染 lockfile、和上游分叉、还要无谓重打整条 Windows 链。fork 与上游发布口径一致即可，C# 高亮功能正常。

## 坑 7：重建 `rw-main` 时 workspace 的 `dist` 声明陈旧，出现并不存在的跨包类型错误（2026-07-24，补充 2026-08-01）

**现象**

- `rebuild-rw-main.sh` 已成功合并候选分支，但紧随其后的 `npm run typecheck` 报新 feature 字段（例如 `codeupForge`）不存在；候选分支的 protocol 源码其实已经定义了该字段。
- 上游同时更新 `packages/relay` 和 client 的加密传输接口后，`npm run build:client` 报 `RelayTransportMessage` 不能传给旧的 `string | ArrayBuffer` transport 声明。

**根因**

- npm workspace 内部包通过生成在 `dist/` 的声明互相解析；`dist/` 不随 Git 分支切换而自动同步。候选分支合并了 protocol/client 源码后，检查仍读取上一个分支留下的声明。后者场景中 client 解析的是 `packages/relay/dist/e2ee.d.ts`，所以只刷新 protocol/client 仍会读到旧 relay 类型。

**解法 / 教训**

- 在候选分支合并完成、执行 typecheck 前，先运行 `npm run build --workspace=@getpaseo/relay`，再运行 `npm run build:client`，刷新 relay、protocol/client 的生成声明。
- 该步骤已写入 `rebuild-rw-main.sh`；不要为了压掉此类错误在调用侧加重复类型或把字段删掉。
- `/home/yangfei/Projects/paseo` 是专用构建 worktree，正常停留于 `rw-main`；chore 和功能分支各用独立 worktree。不要手工在构建目录来回切分支：Git 不会更新被忽略的 `dist`。若构建目录开始时是其他干净分支，统一交给重建脚本切入产品树并先运行 `npm install`。

**不要把源码组合错误误判为 `dist`**

- 如果报错双方都在同一个 workspace 的 `src`/`e2e` 下，例如 `e2e/new-workspace-dictation-submit.spec.ts` 从 `e2e/helpers/new-workspace.ts` 导入一个已不存在的 helper，这不是跨 workspace 声明问题，重跑 `build:server` 没有作用。
- 2026-08-01 的实际案例：最新 `main` 新增测试并调用 `selectWorkspaceIsolation`，而 `feat/worktree-checkout-branch` 已把 helper 改名为 `selectWorkspaceMode`。组合后的 typecheck 才暴露不兼容；正确处理是在该功能分支 rebase `main`，把新测试同步改为 `selectWorkspaceMode`，运行定向测试后推送，再重建 `rw-main`。
- 判断顺序：先看报错路径是否真的落到另一个 workspace 的 `dist/*.d.ts`；只有是，才重建声明拥有方。否则按 Git 归属修复源功能分支。

## 坑 9：重复打包反复重建相同 merge 链和 workspace 产物（2026-08-01）

**现象与根因**

- `main` 和清单功能分支都没变化时，旧 `rebuild-rw-main.sh` 仍创建一套新的 merge commit，再重复跑 format/typecheck/lint；随后服务端和 Windows 又各自重复构建相同的 workspace 依赖。
- Windows zip 默认使用 level 7；同一 payload 的最终压缩约 95 秒，但额外压缩率很小。

**解法**

- `rebuild-rw-main.sh` 反向核对现有 merge 链的每个第一/第二 parent、清单顺序和各分支当前 head。完全一致时直接 no-op；任一分支变化或 `--dry-run` 仍走完整原子重建与检查。
- 完整重建已经刷新 relay/protocol/client 声明。未执行 `npm install` 时，服务端只补 highlight、server、CLI；no-op、重装依赖或前序状态不确定时仍运行完整 `build:server`。
- 同轮 Windows 阶段只补 `@getpaseo/expo-two-way-audio`，不重复 highlight/client。若单独构建 Windows，仍使用完整 `build:app-deps`。
- zip 使用 electron-builder 内置开关 `ELECTRON_BUILDER_COMPRESSION_LEVEL=3`。重复实测为 9.7/10.6 秒、173,003,593 bytes（约 165 MiB）；默认 level 7 为 162,376,829 bytes（154.9 MiB），最终压缩约 95 秒。若快速压缩出现兼容问题，去掉环境变量即可回退默认值。

**边界**

- 只复用 Metro 官方的内容寻址 transform cache；不复用最终 Metro 输出、不手写缓存索引、不替换标准 zip 工具链，也不并行 Android 和 Windows。源码有变化时仍生成最终 bundle 并运行 Hermes。
- 服务端、CLI、protocol 真实入口仍须在每轮检查；复用只减少重复编译，不减少产物验证。

## 坑 10：app Playwright 继承外部 `PASEO_PASSWORD`，隔离 daemon 意外启用认证（2026-08-01）

**现象**

- app 定向 Playwright 测试启动了临时 home 和随机端口的隔离 daemon，但 client 一直连接失败或等待超时；daemon 日志显示 `authRequired=true`。
- `.env.test` 中没有 `PASEO_PASSWORD`，容易误以为隔离 daemon 不会启用密码，继而错误地重建 server `dist` 或重复启动测试。

**根因**

- E2E global setup 构造子进程环境时会展开 `process.env`。dotenv 默认只补充 `.env.test` 中存在的键，不会删除调用 shell 已有的 `PASEO_PASSWORD`。
- 主环境为了 6767 daemon 设置的密码因此被测试 daemon 继承；测试 client 按无密码隔离环境设计，不会自动携带该密码。

**解法 / 教训**

- 所有本地 app Playwright 定向测试显式清空该变量：

  ```bash
  PASEO_PASSWORD= npm run test:e2e --workspace=@getpaseo/app -- \
    e2e/new-workspace-dictation-submit.spec.ts
  ```

- 先看隔离 daemon 日志中的 `authRequired`。若为 `true`，优先检查父进程环境，不要先归因于端口、`dist` 或主 daemon。
- 这只影响测试子进程，不会修改或重启 6767 主 daemon。

## 坑 11：只汇报“成功阶段耗时”会低估用户实际等待时间（2026-08-01）

**现象与教训**

- 一次完整打包从约 19:43 开始，到约 20:36 完成，真实墙钟约 50–52 分钟；其中可构建 `rw-main` 就绪后的服务端、Android、Windows 产物链约 25 分钟。
- 只把最终成功的各阶段相加、扣掉分支修复或失败尝试，会把总时间错误汇报成 14–25 分钟。热 Metro/Gradle 缓存也不能当作稳定基线。
- 后续一律从用户发起 `$build-paseo` 开始计时，到产物校验和下载服务就绪结束。分段耗时用于定位优化点，但不能替代真实总墙钟。

## 坑 12：把构建控制面合进 rw-main，导致脚本来源和产品历史耦合（2026-08-01）

**问题**

- 旧重建脚本从执行目录读取清单，并把 `chore/build-paseo` 当作第一层 merge。chore 里的技能、文档或下载脚本一变，即使产品输入完全没变，也会重写 `rw-main` 并重复仓库检查。
- 如果主构建目录意外停在 `main` 或其他分支，旧流程只能人工切回；直接切换又会留下上一分支的 `node_modules` / `dist`，容易制造假类型错误。

**标准拓扑与处理**

- chore 是唯一构建控制面，只保存清单、技能、脚本和文档；`rw-main` 只由 `main` 与清单功能分支组成，chore 不再是其 ancestor。
- 从 chore worktree 调用控制脚本，并显式指定产品构建目录：

  ```bash
  bash "$paseo_chore_root/dwyanewang/rebuild-rw-main.sh" \
    --build-root /home/yangfei/Projects/paseo \
    --push
  ```

- build root 有改动或处于 detached HEAD 时立即停止；干净的普通分支允许自动切入，失败恢复原分支，成功停留于 `rw-main`。从非 `rw-main` 进入时无条件安装依赖；原本已在 `rw-main` 时，仅在 package、lockfile、补丁或 postinstall 补丁脚本变化时安装。
- 同步 `main` 前先用 `git worktree list --porcelain` 查它是否已签出。已签出就在对应干净 worktree 执行 `merge --ff-only upstream/main`；未签出才允许 `branch -f main upstream/main`。不要直接移动另一个 worktree 正在使用的分支 ref。

## 坑 13：上游用另一种实现吸收功能，原 PR 状态无法避免重复合并（2026-08-02）

**问题**

- 上游可能通过另一个 PR、直接提交或不同架构实现清单分支的同一功能，而原 PR 仍是 OPEN/CLOSED。只在“原 PR 已 MERGED”时删清单项，会继续合并旧实现。
- Git 冲突、typecheck 和 lint 只能发现文本或静态不兼容；两套实现都能编译时，可能留下重复入口、监听、状态或行为。
- patch 等价和路径重叠只能证明补丁/文件关系，不能证明语义；不同实现甚至可能没有任何路径重叠。

**处理**

- 每个清单项分别用 `reviewed-main:<SHA>` 和 `reviewed-head:<SHA>` 记录上次审查的上游 main/功能分支 head，不能用一个全局 SHA 代替：不同分支 fork 基线不同，分支本身也可能 rebase 或 force-push。
- `main` 前进时各项从自己的 main 坐标审查；分支 head 变化时即使 main 不变也重新审查；新分支从自己的 merge-base 开始。同步脚本逐项列出提交和证据，以退出码 `3` 强制暂停。
- 代理必须浏览每项报告的全部提交；疑似相同能力继续读 PR 说明和 diff。完整吸收用 `--remove-branch`，部分吸收回源功能分支 rebase/删重/验证，模糊项询问用户。
- 只有 `--accept-main-review` 精确等于当前 `main` 才把每个保留项的两个坐标推进到当前引用。重建脚本在 no-op、merge 或 npm 前逐项核对，禁止通过直接调用绕过。
- 原 PR 确实合入仍自动删除；patch 等价或路径重叠只做提示，不自动删。审查提交正文记录区间和删改证据，不另建易失的外部台账。
- 首次引入双坐标时，现有项的 `reviewed-main` 只初始化为各自 merge-base，`reviewed-head` 初始化为当前分支 head；下一次同步会有意阻断并要求补做各自的历史区间审查。禁止为了让重建立即通过而直接把所有 main 坐标改成当前值。

## 坑 14：下载脚本误杀端口进程、混用旧产物并假报成功（2026-08-02）

**问题**

- 旧脚本按用户传入端口查 PID，再直接杀监听进程及其父进程；传 `6767` 会威胁主 daemon，其他端口也可能误杀个人服务。
- `PORT`/`TTL` 被拼进 `bash -c`，非法本地参数会被内层 shell 重新解析。
- 固定路径 APK 与“mtime 最新 zip”没有同轮关系；复制或后台启动失败后，末尾成功的 `echo` 还可能把退出码洗成 0。

**处理**

- `serve-dist.sh prepare-build` 在重型构建前删除两个精确目标并记录版本/起始时间；下载时要求 APK 与精确版本 zip 都晚于该标记。
- 下载服务只使用经过数字/范围校验的参数并拒绝 `6767`。它只根据私有状态文件和完整命令身份停止自己启动的独立会话；停止时必须等整个 `setsid` 会话退出，不能只等父进程或单一进程组（`timeout` 可能另建进程组），否则遗留的 `python3 -m http.server` 会占用端口但工作目录已被删除。未知端口占用只报错。
- 主流程使用 `set -Eeuo pipefail`，且在改动前确认 terminal-webview 原本干净；`EXIT` trap 在成功或失败时都只还原这个生成文件。

## 坑 15：Gradle 缓存大量命中，Android 仍在 Metro/Hermes 阶段耗时十几分钟（2026-08-06）

**现象与证据**

- 2026-08-05 末次构建中，原生 `assembleRelease` 为 1175 个任务仅 28 executed、1147 up-to-date，耗时 3m26s；Gradle、`.cxx` 和模块 `build/` 缓存都正常。后续两段流程在确认第一段 bundle 非空后，第二段显式用 `-x :app:createBundleReleaseJsAndAssets` 排除已完成的 bundle，避免仅依赖 UP-TO-DATE 判定。
- 慢的是前一段 `createBundleReleaseJsAndAssets`：29 个任务只有它自己 executed，仍耗时 17m06s。日志明确打印 `Bundler cache is empty, rebuilding`；Metro 从头 transform 5074 个模块就用了 402005ms（约 6m42s），之后还要做整包 Hermes 字节码编译。

**根因**

- React Native 0.81 的 `BundleHermesCTask` 在 Expo `export:embed` 参数前部硬编码 `--reset-cache`。Gradle task 只要因任一 JS/TS 输入变化而执行，Metro transform cache 就被主动清空；Gradle 的依赖、原生和 task history cache 无法替代 Metro 自己的 cache。
- 专用构建目录生成的 `android/app/build.gradle` 还曾残留 `extraPackagerArgs = ["--max-workers", "2"]`，使 20 核机器上的 Metro transform 只用两个 worker。
- Hermes 是同一 Gradle task 内的全量字节码编译，不会因保留 Metro transform cache 而消失。Hermes/NDK 分步仍是防 OOM 的必要稳定性措施，不应为追求速度直接重新并行。

**处理**

- 每次 Expo prebuild 后，从控制面运行：

  ```bash
  bash "$paseo_chore_root/dwyanewang/configure-android-build.sh" \
    --build-root "$paseo_build_root" \
    --metro-workers 8 \
    --hermes-profile local-balanced
  ```

- Expo 的自定义布尔参数从右向左解析重复项；React Native 先放 `--reset-cache`，脚本通过后置的 `--reset-cache false` 覆盖它，不修改 `node_modules`。脚本还会验证当前 Expo 解析语义以及 React Native 的参数先后顺序，依赖升级后若假设失效就直接停止。
- 这只复用按文件内容、transformer 配置等键控的 Metro transform 结果。Gradle 仍根据源码输入决定是否执行 bundle task；执行时仍产出新的最终 JS bundle、source map、assets 并运行 Hermes，因此不是复用旧 APK 或旧最终 bundle。
- `--metro-workers 8` 控制 Metro；第一段 Gradle 的 `--max-workers=1` 继续保留并只控制 Gradle 自己。Metro 与 Hermes 在同一 task 内顺序执行，不会同时达到峰值；若实测内存重新紧张，可显式把 Metro 降回 6，不能通过重新加全局 `--reset-cache` 解决。
- 保留 Metro cache 后的实测中，Metro transform 已从 402.005 秒降至 50.807 秒，但整个 `createBundleReleaseJsAndAssets` 仍需 12m03s；其余约 11m12s 落在 Gradle 配置、Hermes 整包编译和 Source Map 处理。个人本地 APK 因此使用 `local-balanced`：Hermes 继续传 `-O`，仅删除 `-output-source-map`，跳过 Hermes map 输出和 React Native 的 map 合并。它不改变运行时优化，但会失去该 APK 的 JS 崩溃堆栈符号化；需要该能力时传 `--hermes-profile production`。正式/EAS 构建不经过这个本地脚本，不受影响。
- 2026-08-07 最近一次 4-worker 构建中，Metro 在大批源码和依赖变化后转换 5080 个模块耗时 248.288 秒，ARM64 原生段以 4 worker 完成 33 个执行任务、1142 个缓存任务耗时 3m38s。构建机已扩容为 27 GB / 20 核，因此下一档先把 Metro 与原生段分别提高到 8 workers；效果和峰值内存以下一次同口径构建为准，不把热缓存结果当作稳定基线。

## 坑 16：只看单个 PID 或 `top` 截图，无法判断 Android worker 是否真正利用机器（2026-08-07）

**问题**

- Gradle 会继续拉起 Java、Node、Metro、Hermes、CMake 和编译器子进程。`/usr/bin/time -v` 的 Max RSS、对某个 PID 的 `ps`，以及偶然一次 `top` 截图都不能稳定表示整组同时占用的 CPU 与内存。
- 只比较两次墙钟也容易受 Metro/Gradle 缓存冷热和主机调度波动影响。最新 8-worker 构建虽然 Metro 从 248 秒降到约 39 秒，但 Metro/Hermes 整段只快 1分45秒，原生缓存热构建反而从 3分38秒波动到 4分18秒；还不能据此继续加 worker。

**处理**

- 两段 Gradle 都通过控制面的 `profile-build-resources.sh` 运行。脚本为每段建立独立的 systemd transient cgroup，原样继承调用方工作目录和环境，保留 Gradle 退出码，并把结果写到本轮唯一的 `$paseo_build_root/.dev/build-profiles/<时间>-<PID>/`。
- `<label>.samples.tsv` 每秒记录整组 CPU 核心数、占20核整机百分比、当前/峰值内存、当前/峰值 swap、进程数和主机可用内存；`<label>.summary` 给出原命令墙钟、累计 CPU 推导的平均核心数、每秒采样峰值核心数，以及从 cgroup 直接读取的精确内存/swap 峰值。内部 wrapper 在命令结束后只保留一个很短的采样宽限，因此比较阶段耗时看 `command_wall_seconds`，不看包含宽限的 `service_runtime`。
- 原生段平均接近 6～8 核、swap 为0且内存有余量，才能证明8 worker被实际利用；平均不到2核通常表示热缓存下没有足够的并行任务。内存峰值接近22～24 GB或出现 swap 时先降到6 worker。Hermes 若长期只有约1～2核，继续提高 Metro或Gradle worker不会加速该段。

## 坑 17：构建成功后资源包装器等待 90 秒并假失败，第二段又重复 Hermes（2026-08-08）

**现象与证据**

- Metro/Hermes 和 native assemble 都打印 `BUILD SUCCESSFUL`，cgroup 内 command-result 也分别记录 `exit_status=0`；但 transient service 随后停在 `stop-sigterm`，约 90 秒后以 `Failed with result 'timeout'` 结束，旧包装器因此返回 1 并把 summary 平均值写成 `unknown`。
- 同一时段 user systemd 日志持续出现 `Failed to add ... inotify watch descriptor for control group ...: No space left on device`。系统无法可靠收到 cgroup 变空事件，默认 `TimeoutStopSec=90s` 才兜底。
- 自动链被假失败打断后续跑 native assemble；这次 `:app:createBundleReleaseJsAndAssets` 没有命中 UP-TO-DATE，第二段再次运行 Metro/Hermes，native 阶段被放大到 818.769 秒。

**处理**

- transient service 固定 `TimeoutStopSec=3s`，命令结束后的异常 cgroup 清理不再额外等待 90 秒。
- cgroup 内 wrapper 在命令返回后立即原子写 command-result；包装器以其中的退出码、实际命令墙钟、CPU 时间和 memory/swap 峰值为权威数据。`systemd-run` 清理状态单独写入 `systemd_run_exit_status` / `systemd_cleanup_degraded`，不能覆盖真实命令结果。command-result 缺失或格式不完整仍判为采样失败，不能假报构建成功。
- 第一段返回成功后先检查 `app/build/generated/assets/createBundleReleaseJsAndAssets/index.android.bundle` 非空；第二段固定带 `-x :app:createBundleReleaseJsAndAssets`。排除任务只对同一条已验证构建链安全，单独续跑 native 前必须先补齐第一段。

## 其它环境笔记

- **mise 未在 `.bashrc` 激活**：node / java / adb / ANDROID_HOME 等在新 shell 里不可用；进入仓库后运行 `eval "$(mise activate bash)"`，版本始终取 `.tool-versions` / `.mise.toml`，不要硬编码安装目录。
- 判断后台长构建是否真在跑：看日志文件大小是否在增长，别只靠 `ps`/`pgrep`（沙箱里有时看不到后台进程）。
- **产物分发**：三个产物都超过飞书 30MB 文件上限（APK 168MB / exe 110MB / zip 151MB），无法通过飞书机器人直接发文件；`hermes send` 也只支持纯文本，不支持附件。分发只能走下载链接 / U盘 / adb 等。
- **Tailscale 分发不是构建前置条件**：首次设备授权需要人工网页登录；若把它写成打包必过步骤，会因控制面网络波动让已成功的构建误报失败。`serve-dist.sh` 只能复用已授权节点、输出 Tailnet 链接，节点未就绪时继续提供 LAN 地址。Docker 版交互登录不要依赖默认 `containerboot` 的短超时启动器，应使用持久 daemon/状态目录后再授权，否则授权链接会被重启刷新。
